# MUCOM88 繰り返しコンパイルで wasm が落ちる不具合(調査記録)

対象: `upstream/MucomWeb/mucom88/src/cmucom.cpp` の `CMucom::GetTextLine()` /
`CMucom::strpick_spc()`。対症療法として `mucomweb/patches/0005-cmucom-gettextline-bounds.patch`
を適用済み(2026-08-17)。**根本原因は完全には解明できていない**。以下、時系列で分かったことと
分からないままのことを分けて書く。

## 経緯1: 実機報告と最初のヘッドレス再現(440回目)

実機で「新規作成/ライブラリ読込/共有リンク貼付を繰り返すと wasm が
`memory access out of bounds` で落ちる」という報告があった。

`tools/verify_mucom_repeat_compile_crash.mjs` で、3種類の異なる MML
(新規作成雛形/エリーゼのために(Für Elise)サンプル/K パート(ADPCM)ありの短い曲)を順番に
繰り返し `compileMML` すると、**必ず440回目の呼び出し**(SOURCES.length=3で回しているので
147巡目)でクラッシュすることを確認した。実機の落ちる箇所(`mucom88.wasm:0x4c39` 等)と
オフセットが完全一致していた。

分かっていたこと:
- `Module.HEAPU8.length` は最後まで 19,660,800 のまま変化しない(ヒープ枯渇ではない)。
- 単一の MML だけを 600 回繰り返しても再現しない。2種の組み合わせを 1000 回繰り返しても
  再現しない。**3種類を交互に**回して初めて起きる。
- `cf957da`(ミュート機能追加)より前の `3eb5adb` でビルドした wasm でも**同じ440回目に
  同じ場所で**再現した。今日の変更が原因ではない、前から存在するバグ。
- `-sSAFE_HEAP=1 -sASSERTIONS=2` を付けたデバッグビルドで同じ手順を回すと、同じ440回目に
  次のスタックで即死した:
  `CMucom::Play → LoadFMVoiceFromTAG → GetInfoBufferByName → GetTextLine`
  (この時点では `GetTextLine` の `linebuf[mptr++] = *p++;`(範囲チェック無し)が原因だと
  推測していた)

この時点では「範囲チェックを入れて安全な壊れ方に変える」対症療法の方針が決まった。

## 経緯2: GetTextLine だけの境界チェックでは落ちなくならなかった

`GetTextLine()` の `linebuf[512]` への書き込み2箇所と終端の `\0` 書き込みに
`mptr < MUCOM_LINE_MAXSTR - 1` のガードを追加してビルドし直し、同じ再現ハーネスを
回したところ、**依然として440回目に落ちた**。ただしクラッシュ位置が変わっていた:
`-sSAFE_HEAP=1` デバッグビルド + 詳細な `fprintf` デバッグ出力で追跡した結果、実際の
クラッシュは `GetTextLine` の中ではなく、直後に呼ばれる `CMucom::strpick_spc()` の中で
起きていた。

## 経緯3: strpick_spc の本当のバグ(mulchr のデクリメント漏れ)

`strpick_spc()` は `GetTextLine()` が埋めた `linebuf` から `'#'` 行のタグ名部分を
`infoname[64]` へコピーする関数。該当箇所(パッチ前):

```c
mulchr = GetMultibyteCharacter(p);
if (mulchr == 1) {
    *dst++ = tolower(a1);
    p++; len++;
    continue;
}
while (mulchr > 0) {
    *dst++ = *p++;
    len++;
}
```

**この `while (mulchr > 0)` ループには `mulchr--;` が無い。** Shift-JIS の
マルチバイト先頭バイト(`GetMultibyteCharacter()` が 2 を返すケース)に当たると、
`mulchr` は 2 のまま変わらず、ループは自力では終了しない。しかも外側の
`while(1)` ループが持つ `if (len >= strmax) break;` という上限チェックには、
この内側ループが終わって制御が戻るまで到達できない。結果として `dst`
(64バイトの `infoname`)と `p` がひたすら前進し続け、ヒープの無関係な領域を
延々コピーしてから wasm の境界外アクセスで落ちる。

デバッグビルドに `fprintf` を仕込んで実測したところ、クラッシュ直前の1回の
`strpick_spc()` 呼び出しの中で `dst` が開始位置から **60万バイト以上**前進していた
(`mulchr` が確定してから1度も再計算されずに数十万回ループしていたことになる)。

### 単発での再現(440回もループ不要)

`mulchr` バグの仕組みが分かってから、単一の `compileMML()` 呼び出しだけで
即座に落とせる MML を作れた:

```
#テスト用タグ
A @78 T120 o5 l4 v10 cdefgab>c<
```

`#` の直後にスペースを挟まずマルチバイト文字(日本語)が続く行があると、
`ProcessHeader()` がこの行をタグ候補として `infobuf` に格納し、
`GetInfoBufferByName()` が `strpick_spc(linebuf+1, infoname, 63)` を呼んだ瞬間に
`p[0]` が Shift-JIS 先頭バイトのため `mulchr==2` になり、**1回目のコンパイルで
即クラッシュ**した(修正前ビルドで実測、`tools/` に一時スクリプトを作って確認、
検証後削除)。これはパッチ適用後のビルドでは 500 サイクル回しても再現しないことを
確認済み。

一方で、当初の3種類ローテーション(いずれの MML も `#` 直後にスペース無しで
マルチバイト文字が来る行を含まない)がなぜ440回目という一定の回数で同じバグを
踏むのかは、この単発ケースとは別の経路のはずで、**未解明のまま残っている**。
ヒープの再利用パターンにより、以前のコンパイルが残した Shift-JIS っぽいバイト列が
たまたま `linebuf` の「タグ名として読まれる」位置に来る、という仮説はあるが、
実測で裏を取れていない。

## 経緯4: play/stop ライフサイクルは決定的要因ではなかった

「実機では新規作成→再生→停止→…をわずか数回〜9回で踏んだ」という追加報告を受け、
`compileMML()` の連続呼び出しに `Module.stopMusic()` を挟むハーネスを作って検証した。

分かったこと:
- `CompileMML()`(`mucomweb/src/MucomWeb.cpp`)は毎回 `g_mucom` を
  `nullptr` → `make_unique<CMucom>()` で丸ごと作り直し、内部で `Play(0)` も呼んでいる。
  つまり**再生は元から毎回のコンパイルに含まれていた**。明示的な `stopMusic()` を
  挟んでも挟まなくても、上記の「`#` 直後マルチバイト」ケースはどちらも即座に落ちた。
- 逆に、`#` 直後マルチバイトの行を含まない2種類の MML を `stopMusic()` 込みで
  100 サイクル回しても落ちなかった(旧ビルドで実測)。
- 結論: **play/stop を挟むこと自体は再現の必要条件ではなかった。** 決定要因は
  「`strpick_spc()` に渡る文字列の中身(#直後マルチバイト、または3種ローテーションの
  ケースではおそらくヒープ再利用由来の何か)」であって、操作の種類(新規/ライブラリ/
  共有リンク)や再生・停止の有無そのものではないと考えられる。ただし実機の
  「ライブラリ読込→自動再生→停止」を数回で踏んだという報告の実際のMML内容は
  未入手なので、その MML が `#` 直後マルチバイトの行を持っていた可能性が高い、
  という以上の確認はできていない。

## 対症療法の内容(このラウンドで適用したもの)

`mucomweb/patches/0005-cmucom-gettextline-bounds.patch`(`mucomweb/CMakeLists.txt`
から 0001-0004 と同じ冪等適用の仕組みで自動適用)で2箇所を直した:

1. **`GetTextLine()`**: `linebuf[512]` への書き込み2箇所と終端の `\0` 書き込みに
   `mptr < MUCOM_LINE_MAXSTR - 1` のガードを追加。512バイトに収まる通常のケースは
   1バイトも変わらない。収まらない場合は511バイト+終端で打ち切り、
   `#GetTextLine: line truncated to 511 bytes.` を既存のメッセージバッファ経由
   (`vm->Msgf`/`PRINTF`)で出す。
2. **`strpick_spc()`**: 抜けていた `mulchr--;` を復元し(本来ループが意図していた
   デクリメントを戻すだけの、素直な修正)、さらに `len < strmax` のガードを同じ
   ループへ足した(将来 `mulchr` が想定外の値になっても `dest` を超えて書けないための
   保険)。タグ名が普段どおり ASCII だけの場合は挙動が変わらない。

どちらも「振る舞いを変える改造をしない」方針を守り、正常系(512バイト未満の行、
ASCII タグ名)では変更前と出力が一致することを確認している。

## 検証結果

- **陽性対照**: パッチ未適用のビルドで、(a) 従来の3種ローテーション再現ハーネスが
  440回目に確実に落ちること、(b) `#テスト用タグ`(直後マルチバイト)を含む MML が
  1回目のコンパイルで確実に落ちることの両方を実測で確認した。
- パッチ適用後のビルドで、(a) 3種ローテーションを2000回、(b) `#テスト用タグ` を
  含む play/stop サイクルを500回、いずれも無事完走(クラッシュ無し)を確認した。
- 既存の `tools/verify_*.mjs`(このパッチ検証を除く69本)を全て実行し、全PASSを確認
  (`#voice`/`#pcm`/`#title` 等のタグを読む経路の `verify_mucom_voice_name.mjs`、
  `verify_mucom_adpcm.mjs` を含む)。
- 切り詰め(`GetTextLine` 側)が実データで発動しないことを確認: 同梱サンプル
  (`html/*.muc`, `html/*.mml`, `tools/*.muc`, `tools/*.mml`)、および
  `MCM_sample_20190124.zip`(古代祐三氏著作、CC BY-NC-ND 4.0、環境変数
  `MCM_SAMPLE_ZIP` 経由。zip自体もその中身もコミットしていない)から
  `net/d88.js`/`net/song-select.js` で正規に取り出した実曲46枚(候補55件)を
  `compileMML()` に通し、いずれも `truncated` メッセージが出ないことを確認した。

## 直したように書かないための注記

- **上記2件の修正で「なぜ440回目という特定の回数で3種ローテーションが壊れるか」の
  完全な説明はできていない。** `#` 直後マルチバイト行を単発クラッシュとして再現・特定
  できたのは事実だが、当初の3種ローテーション自体はそのパターンの行を含んでいない
  ため、両者が本当に「同じ経路」なのか、ヒープ再利用由来の別経路で偶然同じ
  `strpick_spc` の脆弱点に到達しているのかは未確認。ただし修正の効果自体は両方の
  再現ケースで実測で確認済み。
- `CMemBuf`(`Put`/`PutStr`/`GetBuffer`/`GetSize`)のオフバイワンの可能性、
  タグデータのヌル終端保証の実測は依然として未着手。

## 次に調べるべきこと

1. `CMemBuf` の実装(`Put`/`PutStr`/`GetBuffer`/`GetSize`)を読み、確保サイズや
   再利用(`realloc` 相当)にオフバイワン等の欠陥が無いか確認する。
2. `LoadTagFromMusic()`(`MUBGetTagData` 経由、`.mub` の `hed.tagdata`/`tagsize`)が
   3種類の MML を跨いだときに本当にヌル終端されているかを実測する。
3. 当初の3種ローテーションが440回目で `strpick_spc` の同じ脆弱点(または別の脆弱点)を
   踏む経路を、SOURCES 配列や MML の内容を1つずつ変えて二分探索し、ヒープ再利用仮説を
   検証または反証する。
4. 特定できたら、upstream への追加パッチではなく、まず本プロジェクト側
   (`mucomweb/src/MucomWeb.cpp`)で該当状態を作らないようにする回避を検討する。

## この調査で使った一時ファイルについて

デバッグ用の `fprintf` 計装や、`MCM_SAMPLE_ZIP` から曲を取り出して `truncated`
メッセージの有無を確認するチェックスクリプトは、いずれも調査専用の一時ファイルとして
作業中にのみ存在し、コミット前に削除した(`tools/` には残していない)。再現に使った
分析結果はこのファイルと `tools/verify_mucom_repeat_compile_crash.mjs` の
ヘッダコメントに残している。
