# PMD MMLコンパイラ: 実データ8本の差分分類(2026-08-19)

`#FM3Extend`の`0xC6`実装後、実データ8本(第三者の実在楽曲、MC.EXE ver4.8s実測の参照`.M`)
は全8本ともエラー無くコンパイルできるようになった。ただしバイト完全一致には至っていない
(一致率7.9%〜66.0%、`tools/verify_pmd_real_data_corpus.mjs`で計測、環境変数は同ファイル
参照)。このメモは**実装を直す前の分類作業**の記録で、次回セッションの作業計画に使う。

**実データMML・参照.M本体はどちらも第三者著作物(の派生物)なのでリポジトリに含めない**
(既存の`tools/verify_pmd_compiler_oracle.mjs`と同じ方針)。以下の記述はバイト列の
構造的な観察(オフセット・命令バイト・長さの差)のみで、楽曲の中身(音符列や歌詞に相当する
情報)は含めていない。

## 観察方法

`tools/compare_pmd_m.mjs`の`compareFiles()`(パート単位のprefix一致)を使い、8本×11パートの
一致長・不一致開始オフセットを一覧化した上で、特に差の大きい・パターンが揃っているパートを
`compiler/pmd_mml_compiler.mjs`の`layout.tracks`経由で実バイト単位まで追った。

## 分類(確度の高い順)

### クラス1(確度: 高): SSGパートの`@n`をFM同様の0xff(tone select)として出力しているが、
実機はSSGソフトウエアエンベロープ番号として固定コマンドへ展開している

`compiler/pmd_mml_parser.mjs`の`@`ハンドラ(923-930行目)は、パート種別(`partKind`)を見ずに
常に`{type:'tone', tonenum}`を積む。FMパート(A-F)ではこれが正しい(`0xff`+音色番号)。
しかしSSG(G-I)の`@n`はFM音色テーブルとは無関係で、内蔵ソフトウエアエンベロープ番号を選ぶ
だけ(既存コメント、`compiler/pmd_mml_compiler.mjs`の`fmUsedToneNums`算出コメント参照)。

実データ`MULE_op_loop.MML`のGパート(SSG1)を実バイトで突き合わせたところ:

- 自作: `... fd 0f ff 01 f2 3c 02 02 03 ...` (`fd 0f`=volAbs 15、`ff 01`=tone select @1、2byte)
- 参照: `... fd 0f f0 02 ff 00 01 f2 3c 02 02 03 ...`
  (`fd 0f`=volAbs 15の直後、`f0 02 ff 00 01`=`ssgEnvOld`書式(0xf0+AL/DD/SR/RR、
  5byte)。値はAL=2, DD=-1(0xff符号付き), SR=0, RR=1)

つまり`@1`(SSGエンベロープ番号1)は、実機では`0xff 01`(2byte)ではなく`0xf0 02 ff 00 01`
(5byte、既存の`ssgEnvOld`コマンドと同一書式)に**展開**される。差は+3byte で、多くの
SSGパートで観測された小さい方の長さ差(+3byte)と一致する。

**未確定な点**: エンベロープ番号0-9に対応する固定AL/DD/SR/RR値の対応表は今回1点
(番号1→AL2,DD-1,SR0,RR1)しか実測できていない。実装するには残り8-9点(番号0,2-9)の
実測が必要(WebNP2+MC.EXEで`G @0 c` 〜 `G @9 c`のような最小MMLを1本ずつ流す)。
ADPCM(J)の`@n`(PCM音色番号選択)も同様にFMのtone selectとは別物のはずだが、
今回はSSGの1点しか実測できておらず未確認。

**解消済み(2026-08-19、同日3周目セッション)**: 残り8-9点を`PSENV.MML`
(`G/H`で`@0`〜`@9`を1音ずつ)でMC.EXE ver4.8s実測し、対応表を全10点確定した
(`compiler/pmd_mml_parser.mjs`の`SSG_ENVELOPE_TABLE`)。`@`ハンドラを`partKind==='ssg'`
かつ番号が0-9のときだけ`ssgEnvOld`イベント(`0xf0`+AL/DD/SR/RR)へ展開するよう修正。
ADPCM(J)は実測(`J o4 l4 @0 c @1 c` → `ff 00 30 18 ff 01 30 18 80`)で**展開されない**と
確認できたため、Jはこの分岐から除外し従来通り`tone`(`0xff`+番号)のまま。
FMパートと同じ行にSSGが混在し、範囲外(10以上)の番号がそのままSSGへ流れてくる実データ
実例(`MSO_ET_Virtual_Intensity_88.MML`の`ABI @177`/`GD @183`)があるが、この範囲は
実測が無いため推測で埋めず、従来通り`tone`イベントへフォールバックする(安全側)。
測定用MML(`tools/pmd-reference/pmdssgenv.mml`)は参照`.M`とバイト完全一致を確認済み。

### クラス2(確度: 中): `C`(全音符長)コマンドの重複・順序異常

同じくMULEのGパートで、`C`(measLen、`0xdf`+1byte)が参照側では**2回**現れる
(`transposeAbs`(`0xf5`)の前後に1回ずつ)のに対し、自作は`transposeAbs`の後に1回しか
出力しない。該当MML(`ABCDEFGHIKJ C192 o4 l8`)ではC宣言はファイル中1箇所のみで、
`transposeAbs`(`GHI v15 @1 M60,2,2,3 *1`の`*1`)よりテキスト上前にある。

観測事実:
- 参照は`C`をテキスト順どおり最初に出すが、その**後**にもう一度出す(重複)。
- 自作は`transposeAbs`より後に1回だけ出す(位置もテキスト順と食い違う)。

原因未確定(実装のイベント生成順序の問題か、MC.EXE側が「今のグローバル全音符長」を
何らかのタイミングで再アサートする仕様なのか、切り分けられていない)。次の一歩は
`C`+`*`(転調)だけを使う最小MML(パート単体)をMC.EXEに通し、重複が再現するか、
再現する条件(パートの組み合わせ・宣言順)を1変数ずつ変えて特定すること。

**解消済み(2026-08-19、同日3周目セッション)**: 条件を`PC1`〜`PC9`/`PCA`/`PCB`/`PCC.MML`
(12本、パート指定の組み合わせを1変数ずつ変えた最小MML)でMC.EXE ver4.8s実測し特定した。
**パート指定にFMパート(A-F)が1つ以上含まれ、かつGが含まれる行では、`C`(measLen、
`0xdf`+1byte)の出力がGのトラックにのみ2回出る**(重複するのはGだけ、Cコマンド固有。
同じ行の`v`/`q`/`*`は対象外。FMを含まない行(`GHI`/`GHIJK`)ではGも1回)。原因は不明の
ままだが(MC.EXE内部のFM→SSG境界実装の癖と推測)、バイト一致が目的のためそのまま再現する
実装にした(`compiler/pmd_mml_parser.mjs`のパート分配ループ、`p==='G'`かつ同じ行に
FMパートが含まれる場合、その行で生成された`measLen`イベントだけを複製する)。測定用MML
(`tools/pmd-reference/pmdcdup1`〜`pmdcdupc.mml`)は参照`.M`とバイト完全一致を確認済み。

### クラス3(確度: 高): Kパート(RHYTHM)で`v`/`q`/`*`等の汎用コマンドが未対応として脱落している

`compiler/pmd_mml_parser.mjs`のKパート処理(`tokenizeRhythmKBody`)は「Rパターン選択・
ループ・全体ループ・テンポ・`\`系コマンドのみ対応」で、`v`(音量絶対値)・`q`(ゲート)・
`*`(移調)はKパート単体で書くと「Kパートで未対応の文字です」エラーになる仕様
(既存のエラーメッセージ、`compiler/pmd_mml_parser.mjs`参照)。

実データ`DS4_MAIA.mml`のKパート(RHYTHM)を突き合わせたところ:

- 参照: `f5 00 fc af fd 0e fe 00 e8 2e ea 3f ...`
  (`f5 00`=transposeAbs 0、`fc af`=tempoAbs、`fd 0e`=volAbs 14、`fe 00`=gateAbs 0、
  その後`\`系リズムコマンド`e8 2e`...)
- 自作: `fc af e8 2e ea 3f ...`
  (`fc af`=tempoAbs だけ一致。`f5 00`・`fd 0e`・`fe 00`の3コマンド計6byteが丸ごと欠落)

参照.Mの全体長差(328-322=6byte)ともちょうど一致する。MC.EXEはKパートに対しても
`v`/`q`/`*`(と恐らく他の汎用コマンドも)を受理して出力するが、自作コンパイラは
このMMLがエラーにならずに済んでいる(=該当行はKを含む複数パート指定行で、
K以外の文字だけが解釈されてKの分だけ黙って捨てられていると推測される。要調査:
複数パート指定行でKだけ未対応コマンドをスキップしているのか、あるいはK単体行での
別の理由での脱落かは未確認)。

次の一歩: 該当行(複数パート指定+v/q/*を含む行)がK区画の処理でどう扱われているか
`pmd_mml_parser.mjs`のパート分配ロジックを追い、Kパートでもv/q/*(既に実装済みの
`volAbs`/`gateAbs`/`transposeAbs`と同じイベント種別のはず)を許可するよう
`tokenizeRhythmKBody`の対応コマンド表を拡張することを検討する。

**解消済み(2026-08-19、別セッション)**: 脱落の真の経路は「複数パート指定行でKだけ
未対応コマンドをスキップしている」ではなく、`tokenizeRhythmKBody`内部で`v`/`V`/`q`/`_`/`__`を
**構文としては消費しつつ意図的にイベントを積まず捨てていた**ことだった(パート分配ロジック
自体は元から正しくKへ本文を渡していた)。`v`/`V`は`volAbs`、`q`は`gateAbs`/`gateRandRange`/
`gateMin`、`_`/`__`は`transposeAbs`/`transposeRel`を積むよう修正(他パートの`tokenizeBody`と
同じイベント種別・同じ0xfd/0xfe/0xb1/0xb3/0xf5/0xe7)。ただし`v`の数値変換だけはFM用の
`V_LOWERCASE_FM_TABLE`を適用すると参照と一致せず、実データ実測(`v14`→`fd 0e`=14そのまま)
によりKパートは常に無変換(raw)で積む。DS4_MAIA.mmlのRHYTHM区画はownLength/refLength
とも322→328(参照と一致)になり、パート単位一致長も0→22byteに改善。全体一致率(位置基準の
`wholeFileMatch`)は43.3%→43.1%とわずかに下がったが、パート整列済みの一致率
(`compareFiles().summary.totalByteMatchRate`)は43.7%→44.1%へ改善しており、位置基準指標の
低下はクラス4(ADPCM等のポインタずれ、未解消)がRHYTHM区画の長さ変化で二次的に下流バイト列を
ずらした結果で、この修正自体の後退ではない。詳細は`compiler/pmd_mml_parser.mjs`の
`tokenizeRhythmKBody`内コメント参照。

### クラス4(二次的、独立したバグではない): ADPCM・後続パートのポインタ値のずれ

ADPCM(J)パートは全8本で**出力長は参照と完全一致**するが、内容はほぼ一致しない
(先頭1byteの`0xb4`(PPZ8初期化コマンド)のみ一致し、続く16byteのポインタ値が食い違う)。
これはJ自体のバグではなく、クラス1-3による他パートの長さのズレがヘッダ以降の
絶対アドレス値に波及した結果(RHYTHM/PPZ8トラックのアドレスがずれれば、それを指す
ポインタの値も連動してずれる)。同様に`tone_ptr`の不一致(8本全て)・RHYTHM区画の
不一致(matchedLen 0〜1)もこの因果の下流である可能性が高い。クラス1-3の解消後に
自然と改善するかどうかを再測定するのが妥当。

### クラス5(未分類): `#Detune`/`#LFOSpeed`/`#EnvelopeSpeed` Extendを一切使わない
ファイル(`MSOET`)でもFMパート(A,B,E,F)が部分一致にとどまる

`MSO_ET_Virtual_Intensity_88.MML`はDetune/LFOSpeed/EnvelopeSpeed Extendのいずれも
宣言していないにもかかわらず、FM1/FM2/FM5/FM6パートが早期(offset 28-65byte)で
不一致になる。FM系パートは他パートの長さに影響されない自己完結した領域のはずなので、
これはクラス1-4とは独立した別要因の可能性が高いが、原因は未特定。次の一歩は
該当パートのMML本文と実バイトを1対1で読み合わせること(このメモの作業では
時間の都合で着手できていない)。

## 追記(2026-08-19、クラス1・2解消後の実データ8本再測定)

`tools/verify_pmd_real_data_corpus.mjs`(実データ8本、8/8コンパイル可能を維持)の
「全体一致率(位置基準)」before→after:

| stem | before | after |
|---|---|---|
| INTOPAL | 7.9% | 13.9% |
| MULE | 20.5% | 96.8% |
| POPFUL | 66.3% | 99.8% |
| DS4MAIA | 43.1% | 97.3% |
| MSOET | 50.4% | 49.9% |
| MSOFMFS | 16.9% | 23.6% |
| SSTENG | 55.9% | 78.9% |
| ALPHA | 40.9% | 79.9% |

MSOETのみ全体一致率がわずかに下がっている(50.4%→49.9%)。`tools/compare_pmd_m.mjs`
(パート整列済みの一致率)で調べたところ、一致パート数(2/11)・各パートのprefix一致長は
**変更前後で完全に同一**(パート単位一致率23.15%のまま不変)であり、この修正自体による
後退ではない。原因は範囲外(10以上)の`@n`(`ABI @177`/`GD @183`、クラス1の対象外として
`tone`イベントへフォールバックしている箇所)がSSG1-3トラックの長さを変えないため無関係で、
実際にはクラス2(`C`重複)適用によりGトラックの長さが変わり、クラス4(未解消:
ADPCM/RHYTHM/tone_ptr等のポインタ値のずれ)経由で下流バイト列の絶対位置が動いた結果、
「全体一致率(位置基準)」の指標だけがたまたま0.5pt下がった、という二次的なポインタずれ
(クラス3解消時と同種の現象)。パート整列済みの指標は不変なので実質的な後退は無い。

## 使ったツール

- `tools/verify_pmd_real_data_corpus.mjs`(このセッションで新規作成。環境変数
  `PMD_REAL_SAMPLE_DIR`/`PMD_REF_M_DIR`が無ければSKIP)で一致率の推移を追跡できる。
- `tools/compare_pmd_m.mjs`の`compareFiles()`をアドホックスクリプト(コミットしていない
  一時ファイル)から呼び、パート単位・イベント単位までバイトを追った。
