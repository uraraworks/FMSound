# MUCOM88サンプル曲集46曲でのADPCM(Kパート)再生状況計測

`tools/measure_mucom_adpcm_corpus.mjs` による実測記録。テストデータ(サンプルMML集の
zip)は著作物(CC BY-NC-ND 4.0、古代祐三氏著作)のためリポジトリには同梱しない。
曲データそのもの・MMLの中身はこのファイルにも載せない(曲名の一覧のみ)。

## 実行方法

```
MCM_SAMPLE_ZIP=/path/to/MCM_sample_20190124.zip node tools/measure_mucom_adpcm_corpus.mjs
```

## 実測条件・判定基準(このスクリプトが決めたもの)

- 対象は「サンプルMML集46曲」(`MML_<X>.d88`収録分)。同じzip内のシステムディスク
  (`MUCOM88_V<バージョン>_<X>.d88`)自身が同梱しているデモ曲(`sampl1.muc`等)は、
  `findSongCandidates()`だと再生可能な曲候補として一緒に拾われてしまう(実測: 46曲の
  はずが55件になった。差の9件は3枚のシステムディスクに重複して入っていた
  `sampl1/sampl2/sampl3.muc`)ため、エントリ名の1つ上の階層が`MML_<X>.d88`という
  命名規則に一致するものだけに絞って46曲にした。
- 製品(`html/mucom-app.js`)と同じ前処理を通す: `ui/mucom-voice-resolve.js`
  `resolveMucomVoiceNameRefs()`による`@"名前"`の事前解決、`net/voice-bank.js`
  `findPairedVoiceBank()`による対になるシステムディスクのvoice.dat自動適用
  (`#voice`注入)、標準ADPCMバンク(`html/mucompcm.bin`)の事前読み込み。
- **コンパイル成功** = コンパイルログに`#error`を含まない。
- **Kパートを持つ曲かどうか** = コンパイルログの`[ Total count ]`行にある
  `K:<tick数>`が0より大きいこと。MUCOM88コンパイラ自身の集計を使う(MMLテキストへの
  正規表現より確実。コメント行やタグ行を誤って拾わない)。Kトラックに休符しか
  無い曲も「Kパートを持つ」に含めている(コンパイラがそのトラックにデータを
  割り当てている、という基準)。
- **実際にADPCMが鳴ったか** = レンダリング中に一度でもStatusSnapshotの
  `chstat[OPNACH_ADPCM]`(ADPCMチャンネルのキーオン状態、`mucomvm::GetChStatus(10)`)
  が非0になったこと。絶対値和(absSum)は使っていない(Kパート単体を分離できず、
  他パートの出力に埋もれて誤判定するため)。
- レンダリングは256フレーム刻み(StatusSnapshotの記録粒度)で行い、毎回直後に
  chstatを確認する(取りこぼしなく追える)。**Kパートを持つ曲だけ**レンダリング対象
  にし(Kパートが無い曲はADPCMが鳴りようがないため)、ADPCMキーオンを検出した時点で
  打ち切る(早期終了)。
- **1曲あたりの打ち切り時間: 240秒(4分)ぶんの音声。** 打ち切りまで検出できなかった
  曲は「取りこぼした可能性がある曲」として別枠で数える(黙って除外しない)。

## 結果(2026-08-16実測、zip: MCM_sample_20190124.zip)

| 項目 | 件数 |
| --- | --- |
| サンプルMML集由来の曲候補数 | 46 |
| コンパイル成功 | 46 |
| コンパイル失敗 | 0 |
| Kパートを持つ曲(コンパイラ集計でK側tick数>0) | 40 |
| 実際にADPCMキーオンを検出した曲 | 40 |
| 240秒打ち切りまで未検出(取りこぼしの可能性あり) | 0 |
| 外部音色バンク(voice.dat)を適用した曲 | 39 |
| `@"名前"`の解決に失敗した曲 | 0 |

Kパートを持つ40曲は**全て**ADPCMキーオンを検出できた(40/40)。検出までの
レンダリング時間は最短0.05秒〜最長18.4秒(`bare09.muc`)で、240秒の打ち切り時間内に
全曲収まった(取りこぼしの可能性がある曲は0件)。

Kパートを持たない(コンパイラ集計でK側tick数が0の)6曲: `gh029.muc`, `arg006.muc`,
`arg007.muc`, `arg011.muc`, `arg014.muc`, `sq1_out06.muc`。

## 過去の記録との比較について

この計測より前に「46曲中40曲でKパートが無音だった」という記録が残っているが、
当時の計測手順(判定基準・レンダリング時間・前処理の内容)は残っていない。
本計測とは判定基準が異なる可能性があるため、**「40→40に改善した」という言い方は
しない**(むしろ数字だけ見ると同じ40という値だが、意味は全く別: 当時の記録は
「Kパートが無音だった曲の数」、本計測は「Kパートを持つ曲の数」であり、本計測では
その40曲全てが実際に鳴ることを確認している)。同じ基準で比較できるかどうかが
分からない以上、両者を安易に結び付けて語らない。

## 個別の技術的背景

- 標準ADPCMバンク(`html/mucompcm.bin`)を読み込む修正(`48edad2`)がKパートを
  鳴らす前提条件になっている(`tools/verify_mucom_adpcm.mjs`参照)。
- 解決できない`#pcm`を持つ曲は無音にはならず、標準バンクがそのまま使われる
  (`tools/verify_mucom_adpcm.mjs`のケースD、`README.ja.md`/`README.md`/
  `html/help.html`参照)。
- 対になるシステムディスクのvoice.dat自動適用(`net/voice-bank.js`)と
  `@"名前"`の事前解決(`ui/mucom-voice-resolve.js`)が無いと、外部音色バンクを
  使う曲や非ASCII音色名を持つ曲はコンパイルエラーで落ち、「鳴らなかった」と
  誤って数えることになる(この計測ではどちらも製品と同じ経路を通している)。

## `v255`(最大音量)指定時の音量低下(2026-08-17追記)

親セッションが実測。KパートのみをレンダリングしてPCM絶対値和(absSum、200回×2048
フレーム、標準ADPCMバンク使用)を`v`の値ごとに比較したところ、次の結果になった。

| v値 | absSum |
| --- | --- |
| v50 | 318,765,386 |
| v100 | 614,144,210 |
| v150 | 909,528,062 |
| v200 | 1,204,912,088 |
| v255 | 17,503,824 |

v50〜v200まではほぼ線形に増加するが、**v255だけ桁が1つ以上落ちる**(v200の約1/69)。
「音量を最大にしたら逆にほとんど聞こえなくなる」という、原因の分かりにくい挙動になる。

**この計測で分かっているのはここまで**: v255でPCM出力が実際に小さくなるという事実の
みで、内部で何が起きているか(桁あふれとみられるが、どの計算・どの型で起きているかは
未特定)は追っていない。他のパラメータ(v以外のコマンド、他パートの音量等)で同様の
現象が起きるかどうかも未調査。本項の内容を他のコマンド・値へ一般化しないこと。

利用者向けの注意書きは`html/help.html`(日英)に「v200程度までは上がるがv255では
逆にほとんど聞こえなくなるため最大値は避ける」という実用的な言い回しで載せている
(absSum等の内部指標はそちらには出さない、利用者指示)。
