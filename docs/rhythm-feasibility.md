# MUCOM88 リズムパート(Gパート)を鳴らすための調査

README「できないこと」に記載のとおり、MUCOM88 のリズムパート(Gパート)は
現状鳴らない。直近の調査(`tools/` 側の実測、本文書は参照しない)で、
同梱サンプルMML集46曲中23曲がリズムパートを使うことが分かっている。

本文書は**調査のみ**を目的とする。実装は行わない。**リズム音源の波形データ
(YM2608 実チップのROM由来のPCMサンプル、いわゆる `2608_bd.wav` 等)は
一切取得・複製していない。** `NOTICE.md`「含まないもの」(ROMイメージ・
市販ソフトウェアのデータを一切含まない)という既存方針を前提に、
「仕組み」と「取りうる選択肢」だけを整理する。

「確定した事実」と「推測・未確認」を明確に分けて書く。確定した事実は
すべて `upstream/MucomWeb/mucom88` (本ビルドが実際に使うforkであり、
`upstream/mucom88` 本家ではない)のソースコード直接参照によるもので、
参照は python の `open(path, encoding='cp932')` でCP932を明示デコードして
検索した(素のgrepは2バイト文字をNEL改行と誤認して行を無言スキップするため)。

`upstream/` は `.gitignore` 対象で本リポジトリには存在を確認済み(取得は
していない。既にワークツリーに存在したものを読んだのみ)。

## 1. 仕組み(確定した事実)

### 1.1 `OPNA::Init()` と `rhythmpath`

宣言: `upstream/MucomWeb/mucom88/src/fmgen/opna.h:286`

```
bool Init(uint c, uint r, bool = false, const char* rhythmpath=0);
```

第4引数 `rhythmpath` は既定値 `0`(nullptr)。ヘッダーコメント(19-36行)に
よれば「リズムサンプルのパス」で、省略時はカレントディレクトリ扱い。

定義: `opna.cpp:1247-1269`。本体は `LoadRhythmSample(path)` を呼ぶだけ
(1250行目)で、**戻り値を無視している**(`if` で判定していない)。つまり
リズムサンプルの読み込みに失敗しても `OPNA::Init()` 自体は失敗しない。

### 1.2 期待するファイル名・形式・本数

`LoadRhythmSample()`(`opna.cpp:1301-1384`):

- ファイル名は固定パターン `<path>2608_<NAME>.WAV`。`NAME` は
  `{"BD","SD","TOP","HH","TOM","RIM"}` の6種(1303-1306行)。
  6番目(`RIM`)は `2608_RIM.WAV` が無ければ `2608_RYM.WAV` にフォールバック
  (1327-1331行)。**合計6ファイル**。
- 形式: RIFFヘッダーをオフセット0x10から手動パースし、`"data"` チャンクを
  スキャン(1334-1356行)。検証条件は `fsize < 0x100000`・`whdr.tag==1`
  (リニアPCM)・`whdr.nch==1`(モノラル)(1359行)。条件を満たさなければ
  読み込み失敗扱い。サンプルは `int16` として読み込み、サンプリングレートは
  WAVヘッダーの `whdr.rate` をそのまま使う(1364-1370行、固定レート要求ではない)。
  ビット深度は `int16` 読み込み前提のため事実上16bit固定。

### 1.3 読み込み失敗時の挙動

- ファイルオープンは `FileIO::Open`→内部 `fopen()`(`fmgen/file.h`)。失敗時は
  例外もログも無く単に `false` を返す。
- 6ファイルのうち1つでも開けない/形式不一致だと `LoadRhythmSample()` 内の
  ループが早期break、`if (i != 6)` で全サンプルを解放して `false` を返す
  (1374-1383行)。
- 前述のとおり `OPNA::Init()` はこの戻り値を無視するため、**Init自体は
  常に成功したように見える**。実際に無音になるのは再生時: `OPNA::RhythmMix()`
  (1454-1485行)が `rhythm[0].sample` の非nullをガード条件に含む
  (1456行)。samples が読めていなければ `rhythm[0].sample == nullptr` の
  ままで、リズムミックス処理全体がスキップされる。
  **結論: 失敗はエラーにならず、無音になるだけ。**

### 1.4 呼び出し箇所 — `rhythmpath` は実際に渡されていない

`OPNA::Init` の呼び出しはプロジェクト全体で1箇所のみ:
`upstream/MucomWeb/mucom88/src/mucomvm.cpp:192`
(`mucomvm::InitSoundSystem()` 内)。

```
opn->Init(baseclock, 8000, 0);
```

3引数のみで `rhythmpath` は既定値(nullptr)のまま。この事実は既存の
`docs/right-pane-data.md`(222-233行、「リズム(index9)が常に0であることに
ついて」の節)の記述と完全に一致し、本調査で再確認した。

### 1.5 wasm ホスト側(`mucomweb/src/MucomWeb.cpp`)の初期化経路

- `CompileMML()`(456-476行付近)が `CMucom` を作り `Init()` を呼び、
  内部で `mucomvm::InitSoundSystem()` に到達する(上記1.4の呼び出しに
  つながる)。`MucomWeb.cpp` 内にリズム/PCM/`.wav` 関連のTODOやコメントは
  見当たらない。
- `MucomWeb.cpp` には `FS.mkdir`/`FS.writeFile`/`MEMFS`/`preRun` 等の
  emscripten ファイルシステム操作は**一切見当たらない**(ビルド生成物の
  `build-web/*.js` を除く)。
- ただし `CompileMML()` は仮想パス `/mucom.mub` に対して素の C++ ファイルI/O
  で読み書きしており(443, 459, 474行)、JS側の明示セットアップなしに動作
  している。これは emscripten の既定構成では MEMFS が `/` に自動マウント
  されるためで、`FileIO::Open`(リズムサンプル読み込みが使う関数)も
  プラットフォーム固有APIではなく素の `fopen()` である
  (`fmgen/file.h`/対応する `.cpp`)。
- `mucomweb/CMakeLists.txt` に `-sFILESYSTEM=0`(ファイルシステム無効化)等の
  設定は見当たらない。

**【推測・未確認】** 上記から「Init実行前に `FS.writeFile()`(または
`--preload-file`)でリズムWAVを所定のパスへ置けば `fopen()` 経由で読める
可能性が高い」と考えられるが、**これは類推であり、実際にビルド・実行して
確認したものではない**。リズムサンプル読み込みに特化した既存コードが
このリポジトリに無いため、断定はできない。

## 2. 選択肢の評価

前提: 波形データ自体(実チップROM由来)は本プロジェクトには一切含めない
(`NOTICE.md`「含まないもの」に矛盾しない)。

### 選択肢1: 利用者が自分でデータを用意して読み込ませる

- **(a) 忠実さ**: 実チップのROM由来データそのものなら最も忠実(理論上100%)。
- **(b) 権利**: 配布物ではなく利用者手元のデータを都度読み込ませるだけなので、
  本プロジェクトの「ROM/市販データを含まない」方針と衝突しない。実機PC-98の
  ROM吸い出しと同じ扱い(現に他のOSS実装 `pmdmini` も同方針。README で
  ユーザーに `drum_samples.zip` 等の外部アーカイブ展開を案内している
  ——[`upstream/pmdmini/README.md:19`](../upstream/pmdmini/README.md)、
  データそのものは未取得・未参照)。
- **(c) 実装コスト**: 「ファイルを選ばせてMEMFSへ置いてからInitを呼ぶ」処理を
  追加する必要がある。1.5節の類推が正しければ既存の `Init` 呼び出しの前段に
  ファイル読み込みUIを足すだけで、fmgen側の改修は不要な可能性が高い(未確認)。
  ただし6ファイルの命名規則(`2608_BD.WAV`等)をユーザーに説明する導線が要る。
- **(d) 利用者の手間**: 最大。「自分でリズムサンプルを用意する」行為自体の
  ハードルが高く(入手経路の説明も含め、プロジェクト側が下手に案内すると
  ROM入手を助長しているように見えるリスクがある)、`#voice`/`#pcm` 未対応と
  同様「対応する曲は制約付き」という注記で終える設計とも相性が良い。

### 選択肢2: 自前で合成した代替サンプルを同梱する

- **(a) 忠実さ**: 本物のROM PCMではないため一致はしない。YM2608のリズム音は
  実チップ内蔵ADPCM-Bのサンプル再生であり、公開されている一般的な音源仕様
  文献(YM2608マニュアル等)には「サンプルの中身」までは記載がなく、
  **仕様書から波形データそのものを合成的に導出することはできない**
  (仕様書にあるのはADPCM-Bのデコード方式やレジスタ制御であって、
  収録されている打楽器音のPCM実データではない)。バスドラム/スネア等の
  一般的なドラムシンセ手法(例: サイン波減衰+ノイズでキック/スネアを模擬)で
  「それらしい打楽器音」を自作することは技術的に可能だが、実機の音色とは
  別物になる。
- **(b) 権利**: 完全に自分で合成すれば著作権上もっともクリーン。
  `NOTICE.md`「含まないもの」とも矛盾しない(ROM由来のデータではないため)。
- **(c) 実装コスト**: 中〜大。ドラムシンセの設計・チューニング、6種類分の
  音作り、WAVファイル生成ツールの実装が必要。fmgen側の読み込みパスの
  改修は恐らく不要(1.5節の類推どおりなら既存の `LoadRhythmSample()` を
  そのまま使える)。
- **(d) 利用者の手間**: なし(同梱すれば常に鳴る)。README/NOTICEへの
  「実チップの音とは異なる合成音」という明記は必要。

### 選択肢3: 自由ライセンスで配布されている代替データがあるか

- WebSearch で確認した範囲では、**フリー/オープンライセンスの
  YM2608リズムサンプル代替セットは見つからなかった**。検索結果は
  いずれも「実チップROMからの吸い出し・BIOSアーカイブ」を指しており
  (例: `pmdmini` README が案内する `drum_samples.zip` や
  archive.org 上の PC-8801 BIOS 内 YM2608 rhythm samples アーカイブは、
  いずれも実機ROM由来データの配布であって自由ライセンスの代替品ではない)、
  自由ライセンスを謳う代替音源セットの言及は見当たらなかった。
- **【未確認】** 網羅的な調査ではないため「存在しない」とは断定できない。
  見つからなかった、という状態を報告するに留める。
- 仮に存在したとしても、**データそのものは本タスクの制約により取得していない**
  (ライセンス表記の確認をするとしても、その作業自体は本文書の範囲外とした)。

## 3. 判断材料

### 3.1 既存方針との整合性

- `NOTICE.md`「含まないもの」: 「ROMイメージ(PC-98本体BIOS等)や市販ソフト
  ウェアのデータは、本リポジトリに一切含まれていない」と明記。
  **選択肢1(利用者データ)・選択肢2(自前合成)は矛盾しない。**
  選択肢3は代替データの性質次第(自由ライセンスであれば矛盾しないが、
  現時点でそのようなデータの存在を確認できていない)。
- README「できないこと」に既にリズムパート不鳴りの理由(`rhythmpath`未指定)
  が明記されており、本調査はその記述を裏付ける形になった(1.4節)。

### 3.2 PC-88 (`_emulator/PC88/PC88Behavior`) の前例との類似性

`_emulator/PC88/PC88Behavior/docs/PLAN.md`(読み取りのみ、変更なし)より、
PC-88 ROM問題は4層(L1〜L4)に分割されており、うち **L2(フォント/漢字ROM)**
が本件ともっとも近い性質を持つ:

> L2 — フォント / 漢字 ROM
> **解決済みとして扱ってよい**。美咲フォント・東雲フォント・jiskan16 で
> 置換する。書体(タイプフェイス)自体は原則として著作物ではない
> (ゴナ書体事件・最判 平成12年)。ビットマップの実データはこれら自由
> ライセンスのものを使い、公式ROMからは1バイトも採らない。

これは「実機ROM内のデータを、自由ライセンスの代替データへ差し替えて
機能を回復する」という構図で、本件の**選択肢3**(自由ライセンス代替データ)
と同じ形。ただしPC-88のフォントには美咲フォント・東雲フォント・jiskan16
という**具体的な自由ライセンス代替が実在した**のに対し、YM2608リズム
サンプルについては3.1/選択肢3の調査時点でそれに相当する代替が見つかって
いない。つまり構図は類似するが、**「代替データが実在するか」という
決定的な部分の状況が異なる**(PC-88=見つかった、本件=未発見)。

PC-88 PLAN.md にはもう1つ、本件の選択肢1と対応する考え方がある:
「私物(公式ROM等)は `private/` に閉じ込め `.gitignore` で遮断」
「公開物は第三者が再導出できるものだけで構成する」という設計原則。
選択肢1(利用者が自分のデータを読み込ませる)はこれと同じ思想
——**配布物には実データを含めず、実行時に利用者側から供給してもらう**
——に立っている。

## 4. まとめと調査者としての所感(参考・意思決定ではない)

本文書は調査タスクであり実装判断はしないが、参考として調査者の
所感を記しておく。

選択肢1(利用者が自分のデータを読み込ませる)と選択肢2(自前合成の
代替サンプルを同梱する)は、いずれも既存方針(`NOTICE.md`)と矛盾しない
ことが確認できた。選択肢3(自由ライセンスの代替データ)は現時点で
該当するものの存在を確認できておらず、選択の土台に乗らない。

両立可能な組み合わせとして、**選択肢2(常に鳴る・権利がクリーンな
自前合成)を既定動作にしつつ、選択肢1(自分のROM由来データを読ませれば
それを優先)を上級者向けの上書き手段として用意する**、という設計が
両方の長所(常時動作 / 忠実さが欲しい人への道)を両立できるように見える。
ただしこれは選択肢2の音質的な実現可能性(3.1節「未確認事項」参照)を
試作なしに評価した上でのものではなく、**確証のない所感**であることを
明記する。

- MEMFSへリズムWAVを配置すれば実際に `fopen()` 経由で読めるか

- 自由ライセンスのYM2608リズムサンプル代替が本当に存在しないか
  (WebSearchでの簡易調査のみ。網羅的ではない)。
- `mucomweb/CMakeLists.txt` の emscripten ビルドフラグがファイル
  システムまわりで何かを暗黙に制限していないか(明示的な

- 選択肢2(自前合成)で実際にどの程度「それらしく」聞こえるかは、
