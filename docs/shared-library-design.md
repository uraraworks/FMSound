# アプリ間共有ライブラリ — 設計（調査ベース・未実装）

利用者の理想像: GitHub Pages `uraraworks.github.io` 配下で WebNP2 / WorkbenchNP2 / WebPaint98 /
FMSound が同一オリジンになることを利用し、「実機のドライブのように、アプリごとの保管庫を
切り替えて別アプリのデータへアクセスできる」体験を作る。本ドキュメントは実装前の調査と設計案。
**既存3アプリのコードは調査のみで一切変更していない。**

## 0. 結論だけ先に

- 3アプリは **DBもストアも別々**。相互参照は無い。「共有できる」ことを確認しただけで、
  **実際にIndexedDBを共有した実績はゼロ**（未確認ではなく「調べて、無いと確認した」）。
- 唯一の既存の“共有”は WorkbenchNP2 が WebNP2 を **ビルド時に成果物として取り込む**（vendoring）
  ことで、実行時のデータ共有ではない。
- 4アプリ直結のDB共有は**採用しない**。各アプリは自分のDBを持ち続け、**目録（catalog）専用の
  小さいDBを新設して橋渡しする**方式を提案する（詳細は3章）。

## 1. 既存3アプリの実装（確認した事実）

### WebNP2
- ファイル: `src/storage/db.ts`
- DB名 `webnp2` / version `1` / ストア1つ `images`（keyPath `sourceKey`）
- レコード = `{ sourceKey, url?, name, bytes: ArrayBuffer, savedAt, displayName?, group?, groupName?, groupIndex? }`
- ディスクイメージ本体（FD/HDD、数十MBもあり得る）を **1レコード1ArrayBufferで丸ごと格納**。分割保存はしていない。
- `sourceKey` にプレフィックス規約があり `rom:` `state:` は一覧から除外（`src/api/library.ts`）。ROM本体・セーブステートも同じストアに同居。
- `navigator.storage.persist()` / `estimate()` の呼び出しは**無し**（grep で0件）。
- アプリ間共有の実績: **無し**。ただし `docs/DESIGN.md` に埋め込み公開API（`packages/embed`）があり、
  `scripts/export-embed.sh` が ESM/CSS/型定義/wasm/フォント/ライセンス一式を
  **ビルド成果物として** WorkbenchNP2（旧PC98Dev）側へ同期している。これは「データの共有」ではなく
  「エンジンをライブラリとして埋め込む」経路。

### WorkbenchNP2
- ファイル: `ide/project-fs.mjs`（`IndexedDbProjectFS`）
- DB名 `PC98DevProjectFS`（README曰く「WorkbenchNP2への改名後も旧名のまま据え置き」、理由はコード内コメントに明記：
  名前を変えると別DB扱いになり保存済みファイルが消えるため）
- version `1` / ストア1つ `files`（keyPath `path`）
- レコード = `{ path, content: string, updatedAt }`。**content は文字列限定**（`.asm`/`.c` ソース）。
  バイナリ格納の型は持っていない。「1ファイル＝1プログラム」がREADMEに明記されたモデルで、
  複数ファイルからなる“プロジェクト”という単位は現状無い（flatなpath空間）。
- `ide/vendor/webnp2/` にWebNP2のembed成果物一式（型定義含む）を静的に取り込んでいる＝上記の
  vendoring の受け側。これがWorkbenchNP2側から見た唯一の“共有”。
- `navigator.storage.persist()` / `estimate()` は**無し**。

### WebPaint98
- ファイル: `src/core/vfs.ts`（`IndexedDbVfs`, filerウィンドウ用）と
  `src/core/autosaveStore.ts`（`IndexedDbAutosaveStore`, 自動保存用）
- **DBを意図的に2つに分離**: `webpaint98-filer`（ストア `files`, keyPath `name`,
  レコード `{name, bytes: Uint8Array, mtime}`) と `webpaint98-autosave`
  （ストア `state`, キー固定 `"current"` の単一レコード）。
  分離理由はコード冒頭コメントに明記：自動保存の不具合でユーザーのfiler内ファイル（MAG等）を
  壊さないため、かつDBを分ければ一方のバージョンアップがもう一方の`onupgradeneeded`に影響しない。
  **この「1機能=1DB、影響範囲を物理的に切る」という設計判断は今回の目録方式の根拠として転用できる。**
- `navigator.storage.persist()` / `estimate()` は**無し**。

### 共有の実績まとめ
- **実行時のIndexedDB共有・データ受け渡しは3アプリ間で一切無い。**
- 唯一の既存パターンは WebNP2→WorkbenchNP2 の **ビルド時vendoring**（`export-embed.sh`）。
  これは「エンジンを埋め込む」という別種の結合であり、本タスクが目指す
  「ユーザーデータ（ディスクイメージ・曲・絵）をアプリ間で受け渡す」こととは無関係。

## 2. FMSoundの要件（設計への制約として確認）

- 保存単位は「MML本体 + 付随ファイル（`#voice`/`#pcm`等）」の**集合**であり1曲1ファイルにならない。
  WorkbenchNP2の`files`ストアはpath単位のflat格納なので型としては近い（曲フォルダ配下に複数path、
  という形で流用できる）が、WorkbenchNP2は文字列専用でPMD `.M`等のバイナリは持てない。
  WebNP2/WebPaint98はバイナリ(ArrayBuffer/Uint8Array)を格納できる。
- メタデータ（`#title`/`#composer`等）はMMLヘッダから自動抽出可能 → 目録エントリの`title`等に使える。
- 将来PMDの`.M`をWorkbenchNP2のプロジェクトへ渡す、が最終目的。**現時点でWorkbenchNP2側に
  「他アプリからバイナリを受け取る」経路は存在しない**（`IndexedDbProjectFS`は文字列専用）。
  この経路を作るには少なくともWorkbenchNP2側にバイナリ対応が要る＝WorkbenchNP2自体の変更が必要
  （今回のスコープ外、別タスクとして提起すべき事項）。

## 3. 提案する構造：目録（catalog）専用DBで橋渡しする

### なぜ直結共有にしないか
4アプリが同一のDB/ストアを共有すると、スキーマ変更が波及する。しかも壊れるのは
「公開後、別々のタイミングで更新したとき」＝最も気付きにくいタイミング。
実際、WebPaint98の設計コメント自体が「DBを分ければ影響範囲を物理的に切れる」という
教訓を明記しており、既存の設計思想とも整合する。

### 案
1. **各アプリは自分のDBを今のまま持ち続ける**（WebNP2/`webnp2`、WorkbenchNP2/`PC98DevProjectFS`、
   WebPaint98/2DB、FMSound/新設DB）。**既存3アプリのスキーマ変更は不要**＝今回のタスク制約
   （他リポジトリ不変更）とも一致する。
2. 新設: **`sharedLibraryCatalog`** という独立DB（どのアプリからも読み書きされる、目録専用）。
   - ストア `entries`、keyPathは `id`（例 `"fmsound:<uuid>"` のようにアプリ名プレフィックス付き）。
   - レコードは最小限のメタのみ: `{ id, app: 'fmsound'|'webnp2'|'workbenchnp2'|'webpaint98',
     kind: string（例 'mml-song'|'disk-image'|'mag-picture'|'asm-project'）, title, size,
     updatedAt, ref: { db: string, store: string, key: string } }`
     — `ref` が実体（各アプリ自身のDB内のレコード）を指すポインタ。
   - 実体（Blob/ArrayBuffer/文字列本体）は**目録に置かない**。各アプリの既存DBに置いたまま、
     目録はポインタだけを持つ。これにより「目録を触っても実体スキーマは壊れない」
     「実体スキーマを変えても目録の型は壊れない」を両立する。
3. 各アプリは自分が保存/更新するたびに `sharedLibraryCatalog` へ目録エントリをupsertする
   （実体書き込みと目録書き込みは別トランザクション＝IndexedDBはDBを跨いだトランザクションを
   張れないため、整合性は「目録は実体の存在を保証しない」前提で緩く持つ。他アプリが読むときは
   `ref`で引いて無ければ黙って一覧から外す、という壊れにくい方向に倒す）。
4. 「ドライブ切り替え」UXは `sharedLibraryCatalog` を `app`/`kind` でフィルタするだけの
   読み取り専用ビュー。実体の読み書きは常に**所有アプリ自身のAPIをそのアプリのコードで**
   呼ぶ（＝他アプリのDBスキーマを直接読みに行かない）。これがA節「内部構造を読まない」の実現方法。

### 既存に合わせる場合との比較
既存3アプリは「1機能=1DB」の物理分離を既にやっている。目録方式はこれをアプリ単位に拡張した
だけであり、既存の設計哲学からの逸脱ではない。直結共有（4アプリが1つのストアを直接読み書き）は
既存のどのアプリの設計にも先例が無く、むしろ既存設計が明示的に避けている形なので不採用とした。

## 4. 容量（C節）

- 事実: WebNP2のHDDイメージは1レコードで数十MBになり得る（分割保存無し）。
- 同一オリジンなら4アプリはブラウザの「オリジン単位」の容量枠を共有する。枠が尽きたとき
  ブラウザ（特にChromeのLRU eviction）が消すのもオリジン単位・オリジン内で古い使用順、
  という一般的な既知の挙動（今回はブラウザ実装の話であり3アプリのコード確認事項ではないため、
  ブラウザベンダのドキュメント記載の一般論として扱う＝**個別ブラウザでの実測は未確認**）。
- 現状3アプリとも `navigator.storage.persist()` を**呼んでいない**（確認済み）。つまり今の時点でも
  「WebNP2のHDDイメージがブラウザの都合で消える」リスクは既に存在しており、FMSound追加が
  リスクを新規に生むわけではない。ただし曲データが増えるほど枠の逼迫は早まる。
- 方針案: 目録DB新設のタイミングで、**4アプリ共通で `navigator.storage.persist()` を呼ぶ**
  （どのアプリが最初に呼んでも同一オリジンなら効く）ことを推奨。ただしpersist許可はブラウザ・
  設定に依存し確実ではないため、「消えても壊滅しない」設計（エクスポート/インポート機能を
  各アプリに持たせる。WebNP2は既に`exportDiskBase64`等のエクスポート経路を持っている＝確認済み）
  も併せて残すべき。

## 5. 開発中は別オリジン問題（D節）

公開時（GitHub Pages配下）は同一オリジンだが、開発中は各アプリが別ポートのlocalhostで動くため
別オリジンになり、`sharedLibraryCatalog` の共有は**手元では確認できない**。
検証方法の案:
- 4アプリを**1つのオリジンから配信するローカルプロキシ/静的サーバ**を立てて検証する
  （例: 1つのポートの下に `/fmsound/` `/webnp2/` `/workbenchnp2/` `/webpaint98/` を
  それぞれのdistをマウントするだけの簡易サーバ。ビルド成果物を配信するだけなのでdevサーバの
  HMR等は失われるが、IndexedDB共有の検証には十分）。
- または本番同様に一時的にGitHub Pagesのプレビュー環境（ブランチ・PRプレビュー等）へ実際に
  デプロイして確認する。
- どちらも**このタスクでは未実施**（既存アプリを変更しない制約のもとでの調査止まり）。
  実装フェーズで先に用意すべき最優先事項として明記する。

## 6. スキーマ版管理（E節）

- `sharedLibraryCatalog` のスキーマ変更は、4アプリ全てが参照するため一番慎重に扱う必要がある。
  提案: 目録ストアの `onupgradeneeded` は**追加のみ**（フィールド追加・新ストア追加）を基本とし、
  既存フィールドの意味変更・削除は行わない（v1のリーダーがv2のレコードを読んでも壊れないように、
  未知フィールドは無視するリーダーを各アプリに実装する）。
  破壊的変更が必要になったら新ストア（例 `entries_v2`）を追加し、旧ストアは当面残して両対応にする
  （WebNP2の`webnp2`DBが`rom:`/`state:`プレフィックスで1ストアに複数種別を同居させているのとは
  逆に、目録は将来の版分岐をストア単位で吸収できるようにしておく）。
- 各アプリ自身のDB（`webnp2`/`PC98DevProjectFS`/`webpaint98-*`/FMSound新設DB）は**今まで通り
  各アプリが独立にバージョン管理**してよい。目録はポインタだけなので実体側のマイグレーションに
  巻き込まれない。

## 7. 未確認のまま残った点

- ブラウザのオリジン単位ストレージ退避（eviction）の具体的な閾値・LRU挙動は、各ブラウザの
  ドキュメント記載を一般論として書いただけで、**このオリジン・この構成での実測はしていない**。
- 開発中の別オリジン問題の検証方法は案のみで、**実際にローカルプロキシ等を組んで動作確認はしていない**。
- WorkbenchNP2の`IndexedDbProjectFS`がバイナリ非対応である点は確認したが、
  「PMD `.M`をWorkbenchNP2プロジェクトへ渡す」経路をWorkbenchNP2側でどう実装するか
  （バイナリ対応の追加要否・具体案）は**このタスクのスコープ外**につき未設計。
- FMSound自身の保存先DBの名前・バージョン・ストア構成は、本ドキュメントでは`entries`の型を
  示しただけで**具体的なDB名・ストア設計は未確定**（FMSound側の実装フェーズで別途決める）。
- `navigator.storage.estimate()`を使った実際の残容量監視・警告UIの要否は、要件として
  挙がっていないため**検討していない**（persist呼び出しの要否のみ扱った）。
