# MUCOM88 `#voice` タグ(外部音色バンク)実験記録

**これは実験であり製品採用ではない。** 目的は「`#voice <file>` を通せるか」を
測ることで、通ったこと自体は製品への組み込みを約束しない(採否は別途判断)。
このファイルが参照するパッチ
(`mucomweb/patches/0004-compilemml-processheader.patch`)は
**`mucomweb/CMakeLists.txt` からは適用されない**(冪等適用の対象外)。
`html/` `ui/` `net/` の製品側配線・`mucomweb/src/MucomWeb.cpp` 本体は変更していない
(パッチはリポジトリに残すが、適用後は `git apply -R` で作業ツリーへ差し戻し済み)。

## 0. 前提(確定済み事実。再調査不要として引き継いだもの)

- ビルド対象は `upstream/MucomWeb/mucom88`(同梱fork)。`upstream/mucom88`(本家)ではない。
- `CMucom::Init/Reset` は常に埋め込み既定バンク `bin_voice_dat`
  (`upstream/MucomWeb/mucom88/src/bin_voice.h`、8192byte=256スロット×32byte、
  名前はオフセット26-31)をロードする。
- `#voice <file>` は `CMucom::Compile()`
  (`upstream/MucomWeb/mucom88/src/cmucom.cpp:1244-1250`)内で
  `GetInfoBufferByName("voice")` → `LoadFMVoice()` により機能する**が**、
  `infobuf` は `CMucom::ProcessHeader(char *text)`(cmucom.cpp:1140-1172)が
  MMLを1行ずつ走査して `#` 始まりの行を溜め込むまで空(`NULL`または未初期化)のまま。
- `mucomweb/src/MucomWeb.cpp` の `CompileMML()` は `Compile()` を直接呼び、
  `ProcessHeader()` を一度も呼ばない(grepでは行を読み飛ばす既知の落とし穴があるため
  python `decode('cp932')` で確認済み。文字列 "ProcessHeader" は同ファイルに一切出現しない)。
  → **今回のパッチ適用前は `#voice` タグは常に無視される。**

## 1. 【実測】バイト差分

`tools/experiment_voice_bank.mjs` 内で埋め込み既定バンク
(`upstream/MucomWeb/mucom88/src/bin_voice.h` から実測抽出、md5
`91e674c35e030c76ea99dbc23c963592`)と、サンプルMML集システムディスク
`MUCOM88_V1.7_...ACTRAISER` 内の `voicedat`(先頭8192byte、md5
`b7adcf32a1a0e951a3bd51855a9138bb`)を32byte単位のスロットでバイト比較した。

**結果: 256スロット中235スロットで中身が異なった。**
差分バイト量(絶対値和)が最大のスロットの一つとして **slot29** を主実験に使用。

## 2. パッチ内容

`mucomweb/patches/0004-compilemml-processheader.patch`
(experimental、CMakeLists.txtからは自動適用されない)は
`mucomweb/src/MucomWeb.cpp` の `CompileMML()` に

```cpp
mucomCompiler.ProcessHeader(const_cast<char *>(mml.c_str()));
```

を `Compile()` の直前に1行追加するだけ。`CMucom::CompileFile()`
(cmucom.cpp:1356-1358)が実際に使っている呼び出し順序
(`ProcessHeader(mml); Compile(mml, ...);`)をそのまま踏襲した。
シグネチャ(`int ProcessHeader(char *text)`, cmucom.h:245)はソースで確認済み、推測なし。

## 4. 【実測】判定実験(`tools/experiment_voice_bank.mjs`)

`VOICE_TEST_DIR=<抽出済みdatファイルのディレクトリ> node
tools/experiment_voice_bank.mjs` で実行。`renderFramesForTest()` が返す
PCM絶対値和(absSum)を指標にした。全7チェック **PASS**。

### 陽性対照(パッチと無関係。既定バンク内のみで実施)
既定バンクの slot0 (`@0`) と slot29 (`@29`) をそれぞれ `A l4 @n cdefgab` で
レンダリングして比較:

- `@0`: absSum = 4,107,408
- `@29`: absSum = 9,109,162 (**異なる**)

→ 「スロットの中身が違えば absSum が変わる」ことをエンジン側で確認できた
(この対照が取れて初めて、後段の「変わらない」を意味のある否定として読める)。

### 本実験: 同一スロット番号、`#voice` なし/ありの比較
`@29` を、(1) `#voice` タグなし(常に既定バンク) と (2) `#voice
/voicedat_disk.bin`(MEMFSへ書き込んだACTRAISERディスクの `voicedat`)の
2条件でレンダリング:

- `#voice` なし: absSum = 9,109,162
- `#voice` あり(disk voicedat): absSum = 29,405,772 (**異なる**)
- コンパイルログに `#error` なし。ログには `#load:/voicedat_disk.bin (8192)` と
  `Used FM voice:1` が出力され、外部ファイルが読み込まれたことも確認できる。

### 整合性確認(round-trip)
既定バンクそのものをファイル化し `#voice` 経由で読ませた場合、`#voice` なしと
**完全一致**(absSum = 9,109,162 = 9,109,162)。中身が同じなら結果も同じになる、
という当然の性質が壊れていないことを確認した(パッチが妙な副作用を持ち込んで
いないことの裏付け)。

## 6. 未確認・今回のスコープ外(推測を含む)

- **旧記録(このscratchpadに残っていた `voice_test/` ネイティブ版ハーネスでの
  先行実験)は「ACTRAISERの実曲(`stg001.muc`)で使われている具体的なスロット番号
  (@97/@90/@14/@11/@4/@0/@26等)ではどのデータを与えても `FM Voice not found` で
  失敗した」と記録している。今回の実験(slot29を任意に選んで直接 `@29` で鳴らす)
  はこれと矛盾する結果(成功)になった。** 両者の相違点として考えられる仮説
  (未検証):
  - 実曲が参照する特定スロット番号の `hed` バイト(有効フラグ)が、たまたま
    Z80側コンパイラの検証条件を満たさない値だった可能性(全スロットが
    無条件に有効になるわけではないかもしれない)。
  - ネイティブハーネス側の `CompileFile()` 経路と、今回のwasm側 `CompileMML()`
    +パッチ経路とで、`option` 引数や `CMUCOM_COMPILE_*` フラグの既定値に
    見落としている差がある可能性。
  - この食い違いの真因は**未特定**。「slot29のような単純な指定では通る」ことと
    「特定の実曲の特定スロット指定では過去に落ちた」ことの両方が事実として
    併存しており、後者を今回のパッチ適用後の環境で再現実験していない。
- 個別 `VOICE.n` ファイル(集約 `voicedat` ではなく分割ファイル)の
  スロットへの対応規則は今回も未特定(前回調査からの持ち越し、未解明のまま)。
- 全256スロットのうち235個が異なっていた具体的な楽器名対応は今回は調べていない
  (バイト単位の差分のみ確認、意味的な差の分類は未実施)。

## 7. 結論

**`#voice` タグは、`ProcessHeader()` 呼び出しの欠落さえ埋めれば
(少なくとも今回試した slot29 / ACTRAISERディスクの `voicedat` の組み合わせでは)
機能する。** 外部バンクの読み込みで実測波形(absSum)が変わることを、陽性対照
(既定バンク内でのスロット差)と整合性確認(既定バンクの往復)の両方を伴って
確認した。一方で、旧ネイティブハーネス実験が「実曲の特定スロットでは
依然として失敗する」と記録しており、この食い違いは未解決のまま残る。
**したがって「`#voice` は無条件に生かせる」とまでは言い切れず、
「配線(ProcessHeader欠落)を直せば機能する経路はあるが、特定条件下での
失敗が別に存在する可能性が残っている、未確定」が正確な結論。** 製品コードへの
本採用は、この食い違いを解消してから判断すべき。

## 8. 追加実験: 実曲46曲中12曲での再検証(2026-08-16 その2)

**これも実験。製品コードへの本採用はしない。**

### 8-1. 検証した仮説

第7節の食い違い(旧scratchpadのネイティブハーネス実験が「実曲の特定スロット
参照では `#voice` があっても `FM Voice not found` で落ちた」と記録している点)
について、**「`#voice` とは無関係で、`@"ｿｳﾙﾍﾞ"` のような非ASCIIの音色名参照を
生のまま食わせていたことが原因ではないか」**という仮説を立てて検証した。

根拠: `ui/mucom-voice-resolve.js` の冒頭コメントに実測記録がある通り、
Z80コンパイラは `@"名前"` の名前部分に非ASCIIバイト(半角カナ等)を含むと
`FM Voice not found` で落ちる。製品では `ui/mucom-voice-resolve.js` の
`resolveMucomVoiceNameRefs()` が `@"名前"` を `@番号` へ事前置換してから
コンパイラへ渡すが、旧ネイティブハーネスはこの前処理を経由していなかった
可能性がある。

### 8-2. 対象曲・データ

サンプルMML集(`MCM_sample_20190124`、`net/d88.js`でd88から読み出し)から、
**旧scratchpadの置換前処理実験(`rewrite_report.json`)で `@"名前"` 参照を
含んでいた12曲**を対象にした(このリストは今回新たに選び直したのではなく、
過去に同じ前処理を試した記録から機械的に抽出したもの):

| ディスク | 曲(拡張子無しのファイル名) | 曲数 |
|---|---|---|
| `MML_ACTRAISER.d88` | stg001 | 1 |
| `MML_BARE_KNUCKLE.d88` | stk004, stk013, stk020, stk023, stk027 | 5 |
| `MML_BARE_KNUCKLE2.d88` | bare03, bare04, bare09, bare12, bare16, bare21 | 6 |

各曲に対になるシステムディスクの `voice.dat`(音色バンク本体、先頭8192byte=
256スロット)を組にした: `MUCOM88_V1.5_ACTRAISER.d88` /
`MUCOM88_V1.5_BARE_KNUCKLE.d88` / `MUCOM88_V1.7_BARE_KNUCKLE2.d88`。
**`ALGARNA` と `SLAP_FIGHT_MD` は対になるシステムディスクがzip内に存在しない**

### 8-3. 実験方法

第2節のパッチ(`ProcessHeader()` 呼び出し追加)を適用・ビルドした上で、
`net/d88.js` (`readD88MmlText`/`readD88FileBytes`)で曲本文とシステム
ディスクの `voice.dat` をそのまま製品と同じ復元経路で取り出し、
`ui/mucom-voice-resolve.js` の `resolveMucomVoiceNameRefs()`(製品の
`@"名前"`→`@番号` 置換そのもの)を通した上で、4条件でコンパイルした:

- A: 名前置換なし + `#voice` なし
- B: 名前置換あり + `#voice` なし (現在の製品の状態)
- C: 名前置換なし + `#voice` あり (過去の失敗を再現するはずの条件)
- D: 名前置換あり + `#voice` あり (仮説が正しければ成功するはずの条件)

`#voice` ありの条件では、曲とペアのシステムディスクから取り出した
`voice.dat`(8192byte)をMEMFSへ書き込み、`#voice <path>` をMML先頭に追加した。
判定はコンパイルログを文字列(latin1デコード)として見て `#error` /
`not found` の有無で成否を判定し(grepは使っていない)、成功時は
`renderFramesForTest()` のabsSumを記録した。

### 8-5. stk023だけD(仮説成功条件)が失敗した件の原因

**仮説は外れていない。原因は特定でき、`#voice` 自体の欠陥ではない。**

stk023のMML本文には `@"ｿｳﾙﾍﾞ "`(半角カナ5文字+**末尾に半角スペース1文字**、
計6バイトで名前フィールドをちょうど埋め切っている)という参照が1箇所ある。

`ui/mucom-voice-resolve.js` の名前表は、埋め込み既定バンクの各スロット名
から**末尾の空白(0x20)/NUL(0x00)パディングを除去したもの**をキーにしている
(スロット側のパディング方式が不統一なための正規化)。一方 `@"名前"` 側の
クエリ文字列はそのまま(パディング除去なし)でエンコードして照合するため、
末尾に本物のスペース文字を含む `"ｿｳﾙﾍﾞ "` は、キー`"ｿｳﾙﾍﾞ"`(スペース無し)
と一致せず**未解決のまま**残る(実測: `resolveMucomVoiceNameRefs()`の
`unresolvedNames`に`'ｿｳﾙﾍﾞ '`が1件だけ入る)。

この未解決の非ASCII参照は、B条件(埋め込み既定バンク、`#voice`なし)では
**たまたまコンパイルが通った**(実測: `Used FM voice:11`のログとともに成功)。
D条件(外部`voice.dat`を`#voice`で読み込む)では**`FM Voice not found`で
失敗した**(実測ログに明記)。B側で通った理由の詳細な機構(埋め込みバンク側の
名前照合が非ASCII込みでもこの特定バイト列とだけ一致した経路)までは
今回は特定していない(未確認・推測: 埋め込みバンクの名前テーブルに
末尾スペース込みでバイト完全一致するエントリが実在する可能性がある)。

いずれにせよ、**この1件の失敗は「`@"ｿｳﾙﾍﾞ "`という末尾スペース付きの
非ASCII参照を、現行の`ui/mucom-voice-resolve.js`が正規化しきれていない」
という別の(既知の設計方針から予見できる)限界であり、`#voice`タグの
機構そのものの欠陥ではない**。11/12曲は仮説どおりC失敗・D成功で説明が
つき、この1件も原因を突き止めた上で仮説と矛盾しないと判断できる。

### 8-6. 旧記録(第7節)のどこが誤りだったか

第7節で「食い違い」として持ち越していた旧ネイティブハーネス実験の記録
(実曲の特定スロット参照で`#voice`があっても`FM Voice not found`で
落ちた)は、**`@"名前"`形式の非ASCII音色名参照を、製品の
`ui/mucom-voice-resolve.js`による事前置換を経由せず生のままコンパイラへ
渡していたために失敗していた可能性が高い**。今回、製品と同じ前処理
(名前置換)を通した上で同じ実曲12曲(旧scratchpadの置換前処理実験と
同じ曲)を試したところ、12曲中11曲で明確に成功し、外部バンクの内容が
実際に音(absSum)へ反映されることを確認した。

**したがって「`#voice`は実曲では機能しない」という旧記録の含意は誤りで
あり、正しくは「実曲のMMLが使う`@"名前"`形式の音色参照は、名前置換という
別の前処理を経由しない限り(非ASCII名の制約により)そもそもコンパイルが
通らず、`#voice`の有無に関わらず失敗する。製品の名前置換を通せば
`#voice`は実曲でも機能する」**が正確な理解。

### 8-7. 結論(第7節の更新)

- **確定した事実**: 実曲46曲中12曲(`@"名前"`形式の音色参照を含む曲)で、
  製品と同じ名前置換前処理を通した上で`#voice`タグを使うと、11/12曲で
  コンパイルが成功し、外部音色バンクの内容が実際の波形(absSum)に反映
  されることを実測で確認した。残り1曲(stk023)の失敗原因も、`#voice`とは
  独立した名前解決側の既知の限界(末尾スペース付き非ASCII名の正規化漏れ)
  として特定できた。
- **推測・未確認**: stk023でなぜB条件(埋め込みバンク)側だけ通ったかの
  Z80側の内部照合機構の詳細/`ui/mucom-voice-resolve.js`の末尾スペース
  正規化漏れそのものを製品側で直すべきかどうかの判断/個別`VOICE.n`
  ファイルのスロット対応規則は今回も未特定。
- **結論**: 第7節の「未確定」は解消した。**配線(ProcessHeader欠落)を直し、
  製品の名前置換前処理(`ui/mucom-voice-resolve.js`)を経由させれば、
  `#voice`タグは実曲でも生かせる**ことを実測で確認した。ただし
  これは実験結果であり、製品コードへの本採用(ProcessHeader呼び出しの
  追加、および名前正規化の末尾スペース対応の要否)は別途判断すべき。

## 9. 製品採用(2026-08-16、このファイルより後の実装)

このファイル自体は実験記録として残すが、`#voice`(外部音色バンク)は
その後、以下の形で製品として採用された(実装はこのファイルの更新後に
別途行った。詳細はコミット履歴・各ファイルのコメント参照):

- パッチ0004(`mucomweb/patches/0004-compilemml-processheader.patch`)は
  `mucomweb/CMakeLists.txt`の冪等適用対象(4本目)に組み込み、かつ
  `ProcessHeader()`呼び出し自体を`mucomweb/src/MucomWeb.cpp`へ直接コミット
  した(0001-0003と違い対象ファイルがFMSound本体の直接管理下にあるため、
  通常運用ではCMake側の適用は「既に当たっている」を検出して何もしない
  保険として働く)。
- 対になるシステムディスク(`MML_<X>.d88` ↔ `MUCOM88_V<バージョン>_<X>.d88`)
  の`voice.dat`を見つける層を`net/voice-bank.js`として新設した。
- 名前解決(`ui/mucom-voice-resolve.js`)は、外部バンクを使う曲では
  「①そのバンク自身の名前表→②見つからなければ既定バンクの表」の順で
  解決するフォールバック連鎖にした。**実測(対になるシステムディスク8枚
  全数)で、ディスクの`voice.dat`の名前フィールドは埋め込み既定バンクの
  名前と1件も一致しなかった**(重複0件)。フォールバック無しだと、
  既定バンクでなら解決できていた`@"名前"`参照(本節8-4の`stg001`の
  `@"ﾎﾟｰﾗﾍﾞ"`等)が軒並み未解決のまま残り、46曲中14曲が新たにコンパイル
  失敗する(実測)。この事実により、8-4で「B=D(絶対値和が一致)」と
  記録したstg001の説明(該当パートがv0=無音のため)はそのまま製品でも
  成立する一方、「外部バンク自身の表で名前を引く」という要求は
  この実データの範囲では常にフォールバック側(既定バンクの表)へ落ちる、
  という結果になった(機構そのものは合成データで別途検証。
  `tools/verify_mucom_voice_name_bank.mjs`参照)。
- 曲ライブラリ(IndexedDB、`net/library.js`)は、対になるバンクが見つかった
  曲について、そのバンクのバイト列(8192byte)も`voiceBank`フィールドとして
  一緒に保存する。理由: 保存しないと次回ライブラリから開いたときだけ音が
  既定バンクへ戻ってしまう退行になるため。
