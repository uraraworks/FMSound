# PMD 側で MML 編集を実現できるか — 選択肢調査

MUCOM88 は wasm 化した `CMucom::Compile()` によりブラウザ内で MML→再生が完結するが、
PMD 側（`upstream/98fmplayer` の `fmdriver_pmd.c`、`upstream/pmdmini`）は再生専用の
C 再実装であり、MML→`.M`/`.M2` のコンパイラを持たない。この非対称を解消できる見込みが
あるかどうかを調べた。

## 2. PC-98 エミュレータ上で公式コンパイラを動かす道

### WorkbenchNP2 の実際の仕組み（README.md を確認）

**重要な訂正**: WorkbenchNP2 は「ゲスト内で公式コンパイラを CPU エミュレーション上で実行する」方式では**ない**。実際の構成は：

```
.asm ──[wasm NASM]──> .COM ──[FAT12 書き込み]──> .xdf ──[WebNP2]──> PC-98 で実行
```

つまり **コンパイル自体は wasm 化した NASM / SmallerC（ホスト側 JS 環境）が担い、WebNP2（PC-98エミュレータ）は生成済みバイナリの「実行・デバッグ」だけを担当する**。C 側も同様に SmallerC を wasm 化してホスト側でコンパイルしている。ゲストの CPU 上で `.EXE` 形式のコンパイラそのものを走らせて出力を取り出す、という使い方の実績はドキュメント上確認できなかった。

一方で、この案が要求する「ゲスト実行ファイル（MC.EXE）を PC-98 上で走らせ、結果ファイルを取り出す」ために必要な**要素技術はほぼ揃っている**：
- FAT12 イメージへの任意ファイル書き込み（`toolchain/fdadd.mjs`）と、既存イメージの新規生成（`makefd.mjs`）
- WebNP2 上でのブート・実行・4B01h ローダによる対象プログラムの起動と終了検知（デバッガ実証セクション）
- FD ホットスワップ手順（排出→間隔→挿入→間隔、DOSの再試行/中止での復旧）が実測・documented 済み（PC98プロジェクトの記憶: `feedback_webnp2_fd_swap_needs_eject.md` 等）

つまり **WorkbenchNP2 と全く同じ実績があるわけではないが、その部品を転用すれば「MC.EXE をゲストで自動実行し、`.mml` を渡して `.M` を回収する」パイプラインは実現可能性が高い**。ただし以下は新規の実装が要る：
- MC.EXE 本体の入手（前述の通りミラーにバイナリなし。ビルドが必要なら OPTASM 入手性が未確認のボトルネック）
- 自動実行フロー（AUTOEXEC.BAT や COMMAND.COM 経由でのコンパイラ起動、完了検知の合図をどう取るか）の設計・実装
- 出力 `.M` ファイルを FAT12 イメージから読み出す機構（現状 `fdadd.mjs` は書き込み方向、読み出し方向は未確認）

### 再配布条件（KAJA氏）

readme.txt（`d2lmirrors/pmd` 経由で確認）に「ソースについての著作権は放棄しませんが、ご自由に使って頂いて構いません」とあるのみで、正式なライセンス文言（再配布可否・改変物の扱い等）は**ない**。**同梱可能かどうかは法的にグレー**であり、少なくとも「ソースコードを自由に使ってよい」という許諾は確認できたが、コンパイル済みバイナリ（MC.EXE）自体の配布慣行・許諾については本調査では**未確認**。安全側に倒すなら「FMSound には同梱せず、利用者が自分で入手した MC.EXE をブラウザにアップロードして使う」形が無難。

### 現実性の評価

- **速度・操作性**: DOS 上でのコンパイルは一瞬で終わる処理のはずだが、PC-98 CPU エミュレーションの起動・FD交換・完了検知を挟むため、体感の応答性は wasm 直接コンパイル（MUCOM88方式）より確実に劣る。MUCOM88 は「エディタで打鍵→即再生」だが、この経路は「エディタで編集→仮想FDへ書き込み→エミュレータ起動/交換→実行→検知→読み出し」という多段になる。
- **実装量**: WorkbenchNP2 の FD 生成・交換・実行検知の資産を再利用できる分、ゼロから作るよりは相当省力化できる。ただし「完了検知」（MC.EXE 終了をどう捉えるか）と「出力ファイルの回収」は PMD 向けに新規設計が要る。中〜大規模の作業（週〜月オーダー、要見積もり）と見るのが妥当で、正確な工数は**未確認**。

## 3. その他の道

### (a) `.M` フォーマットを直接生成する独自コンパイラ

- 読み出し側の実装は `upstream/98fmplayer/fmdriver/fmdriver_pmd.c`（6114行、BSD 2-Clause）として既に存在し、フォーマット理解の手掛かりになる。
- さらに KAJA氏自身が書いた仕様書 `PMDMML.MAN`（`d2lmirrors/pmd/mc/PMDMML.MAN`、氏の公開ソース一式に同梱）が一次資料として存在するため、**MC.ASM のコードを読む（≒派生の懸念が生じる）のではなく、公式マニュアルと 98fmplayer の再生実装を仕様として、独立実装のコンパイラを新規に書く**という経路が成立しうる。
  - これは「他人の実装を読むほうが自分で測るより危ない」という方針（由来の鎖の問題）とも整合し、法的にも最もクリーンな部類に入る。
  - ライセンスも FMSound 側で自由に選べる（GPLv3 に縛られない）。
  - 規模感: MC.EXE 自体がそれなりの機能を持つコンパイラであり、`fmdriver_pmd.c` の再生側が6000行超であることから、対応する音色/エフェクト全部を作り込むコンパイラは軽くはない。ただし基本的な音符・音長・音色設定だけの MVP に絞れば段階的に着手可能。**正確な工数見積もりは未確認**（要件次第で大きく変わる）。

### (b) 対応ドライバを PMD 以外にも広げる（FMP）

- `upstream/98fmplayer` は **FMP ドライバの再生**（`fmdriver_fmp.c`）にも既に対応済みで、FMDSP 表示も共通基盤上で使える可能性が高い。
- FMP のコンパイラ（FMC）もソースが公開されたという情報があるが、一次配布元・ライセンスとも本調査では**未確認**。PMD より調査が浅い段階であり、有望かどうかの判断はまだ下せない。

## 結論

**PMD 側でも MML 編集を実現できる見込みは「ある」。** ただし「MUCOM88 と同等に軽量な、静的Webアプリ内wasmコンパイラ」を最速で得る決定打（そのまま移植できる C/C++ のOSSコンパイラ）は見つからなかった。

もっとも現実的な経路の評価は次の通り：

1. **最有力（推奨）**: `.M` フォーマットの独自コンパイラを新規実装する（3-(a)）。
   - 法的にクリーン（KAJA氏公開のマニュアルと98fmplayerの再生実装を仕様として使い、コードは読まない）。
   - ライセンスを自由に選べる（GPLv3の伝播を回避できる）。
   - MUCOM88と同じ「wasm不要・素のJS/TSで完結」という静的Webの性質を保てる。
   - 欠点は自前実装の工数。MVP（基本音符+簡易音色）から段階着手すれば現実的。
2. **次善**: PC-98 エミュレータ上で MC.EXE を自動実行する経路（2章）。
   - WorkbenchNP2 の要素技術（FAT12読み書き・FD交換・実行検知）は転用できるが、「ゲスト内コンパイラを走らせて結果を回収する」使い方そのものは前例がなく新規設計。
   - MC.EXE バイナリの入手・配布可否がグレー（ソース公開の許諾はあるが正式ライセンスではない）。
   - 体感速度・UXでは (1) に劣る。
3. **保留/要追加調査**: PMDDotNET のロジックを参照する、または FMP 経路を深掘りする。
   - PMDDotNET は GPLv3 なのでコードを直接取り込むと当該部分がGPLv3化する制約がある。
   - FMP はライセンス・一次配布元とも未確認で判断材料が不足。

## ドライバ本体の入手性

PMD.COM 本体（`PMDB2`/`PMDPPZ`/`PMDPPZE`/`PMDVA` 等の派生を含む）について、
**MC.ASM（コンパイラ）だけでなくドライバ本体のソースも同じ2019年公開に含まれている**ことを、
GitHub API でリポジトリのファイル一覧を直接取得して確認した（一次情報）。

### (1) ソース公開の有無 — **公開されている**

- 一次情報のミラー: https://github.com/d2lmirrors/pmd
- `git/trees` API（`https://api.github.com/repos/d2lmirrors/pmd/git/trees/master?recursive=1`）で
  取得したファイル一覧に、ドライバ本体のアセンブラソースが実在することを確認した：
  - `pmd/PMD.ASM`, `pmd/PMDB2.ASM`, `pmd/PMD86.ASM`, `pmd/PMDPPZ.ASM`, `pmd/PMDPPZE.ASM`,
    `pmd/PMDVA.ASM`, `pmd/PMDVA1.ASM`（PC-98版ドライバ本体・各派生）
  - `pmdibm/PMDIBM.ASM`, `pmdibm/PMDL.ASM`, `pmdibm/MC.ASM`（IBM PC版）
  - `pmp/PMP.ASM`（プレイヤ本体）
  - `mc/MC.ASM`（既述のコンパイラ）
- **必要なアセンブラ**: `pmd/assemble.bat` の中身を直接取得して確認したところ、
  既定は `optasm pmd; ... optlink pmd,pmd.com;` で **OPTASM/OPTLINK（商用・非公開）** を使う。
  ただし同フォルダに **`asm_masm6.bat` / `asm_masm8.bat` も同梱**されており、
  中身は `ml /omf /Zm pmd.asm` ... `link16 pmd,pmd.com;` という
  **Microsoft MASM（`ml.exe`）でのビルド手順**だった（一次情報：raw ファイルを直接取得して確認）。
  これは既存記述（OPTASM必須・入手性未確認）を修正する新情報で、
  **MASM 6/8 系でもビルド可能な経路が用意されている**ことが分かった
  （実際に手元でアセンブルして COM が動くかまでは本調査では未検証）。
- **ライセンス・許諾**: ドライバ本体もコンパイラと同じ `readme.txt` 1本の下にまとめて公開されており、
