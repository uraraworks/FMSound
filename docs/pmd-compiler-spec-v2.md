## 1. パート指定文字 `J` / `K`（出力構造の追加）

これは構文追加ではなく、**ヘッダのパートポインタが増える**変更である。

### 1.1 PMDMML.MAN側の定義

`PMDMML.MAN §1-1-3`「パート記号と音源の対応」は音源/ドライバの種類ごとに6通りの表を載せている。
本プロジェクトの既存実装(v1 7.3節)は表2「**PMDB2.COM / PMD86.COM / PMDVA.COM の場合**」
（A-F=FM1-6, G-I=SSG1-3）を採用済みなので、本書もこの表で確定させる:

```
A FM音源1   B FM音源2   C FM音源3   D FM音源4   E FM音源5   F FM音源6
G SSG音源1  H SSG音源2  I SSG音源3
J PCM音源
K リズムパターン指定
R リズムパターン定義
任意1/2/3  FM音源3（#FM3Extend, →§2-18）
```

`J`=PCM(ADPCM)、`K`=リズムパターン指定、`R`=リズムパターン定義、という**3種の別パート**である
（`R`は再生パートではなく、`K`が参照するパターン定義データの置き場）。

実データでの出現数（3曲中）: `K`=3曲、`J`=2曲。`R`は`K`と対で使われるため、`K`を使う3曲は
すべて`R`行も持つ（未対応エラーの集計は`K`行が先に「未対応のパート指定」で弾かれるため、
`R`は別カウントされていない可能性が高い。実データで`R`行の存在は目視確認した）。

### 1.2 `J`（ADPCM）: ヘッダindex 9、既存の11パートポインタ表の空きスロット

出典: `fmdriver_pmd.h:24`（`PMD_PART_ADPCM`はenumで9番目、FM1-6(0-5)+SSG1-3(6-8)の直後）。
v1 1.2節で確定済みの「ヘッダの11パートポインタ表(相対`0x00`〜`0x14`)は`pi<=PMD_PART_RHYTHM`
の範囲」に**ADPCMは既に含まれている**（index9）。つまり`J`パートの追加に新しいヘッダフィールドは
不要で、**現状「常に空トラック」にしているindex9のスロットへ実トラックを書けばよいだけ**。

トラックのバイト書式はFM/SSGと共通（`tools/verify_pmd_channel_mute.mjs:53-54`のコメントが
出典付きで既に確認済み: `0xff`=音色/サンプル番号選択(`pmd_cmdff_tonenum_adpcm`,
`fmdriver_pmd.c:2307`)、続けて通常の音符バイト）。**両方の一次情報が一致**: `PMDMML.MAN §1-1-3`
は`J`を「PCM音源」という独立パートとして説明するのみで書式の特記はなく、`fmdriver_pmd.c`側の
実装が「FM/SSGと共通のコマンド体系」であることを裏付ける。

音量・パン等ADPCM固有の値域（`V`=0-255等）は`PMDMML.MAN §5-2`に記載済みで、v1 7.2節がすでに
FM/SSGの値域差を扱った実績があるため、実装方針は明確（新しい未解明は無い）。

### 1.3 `K`/`R`（リズム）: 通常のパートとは全く違う2階建て構造

`K`はヘッダindex10（`PMD_PART_RHYTHM`）のポインタが指すトラックを持つが、**その中身は
音符ではなくR定義パターンへの索引**。`R`はヘッダに専用スロットを持たず、**`r_offset`
フィールド（v1 1.1節で既出、相対`0x16`-`0x17`）が指す「256エントリ×2byteの索引表」**へ
書き込まれる。

**Kトラックの中身**（`pmd_part_proc_opnarhythm`, `fmdriver_pmd.c:1740-1751`。既存の
v1/8章とは独立に今回精読して確定）:
- 1バイト`cmd`を読む。
- `cmd == 0x80`: トラック終端（他パートと共通のマーカー、ループ判定も同じ`loop_ptr`機構）。
- `cmd & 0x80`かつ`!= 0x80`: 通常パートと同じ`0x81`以降のコマンド体系（`L`/`[`/`]`等、
  cmd_table_rhythmの表引き）。
- **`cmd < 0x80`**: `ptr = r_offset + cmd*2`（`fmdriver_pmd.c:1748`）の位置にある2byteポインタ
  (LE)を読み、それを「現在のRサブストリーム位置」(`pmd->r_ptr`)にセットする。
  つまり**`cmd`の値がそのままRパターン番号**であり、MMLの`Rn`はこのバイトをそのまま
  出力するだけでよい。

  **§6-7の[範囲]は0-255だが、この読み出し経路は`cmd<0x80`のときのみ発動するため、
  実際に到達可能なパターン番号は0-127に限られる**（`cmd&0x80`が真の場合は上記の
  「コマンド体系」に分岐してしまい、パターン索引としては解釈されない）。
  これは`PMDMML.MAN`と`fmdriver_pmd.c`が**食い違った**箇所であり、**未解明として残すのではなく
  食い違いそのものを確定事実として記録する**（範囲外の128-255がMC.EXE側で別処理される
  可能性はあるが、MC.EXEのソースは参照していないため未確認）。v2実装では**Rパターン番号は
  0-127のみ受理**するのが安全側。

**Rサブストリームの中身**（`fmdriver_pmd.c:1721-1785`。v1 1.5節で「未解明」としていた
14bitマスクのビット割当を、今回`pmd_ssgrhythm_opna_table`(`:5310-5322`)を精読して確定した）:

1回分の打点は次の3パターンのいずれか（1バイト目`rcmd`で分岐）:
- `rcmd < 0x80`: 休符（無音）。続く1byteが長さ。
- `rcmd & 0xc0 == 0x80`（bit7=1, bit6=0）: 打点マスク。`((rcmd<<8)|次の1byte) & 0x3fff`が
  14bitマスク（bit0-10のみ意味を持つ、下記表）。続く1byteが長さ。
- `rcmd & 0xc0 == 0xc0`（bit7=1, bit6=1）: **通常パートのコマンドバイトへのエスケープ**
  （`fmdriver_pmd.c:1785-1793`。`part->ptr`と`pmd->r_ptr`を一時的に入れ替えて
  `pmd_part_cmd_rhythm`を呼ぶ）。この分岐の詳細な用途（Rサブストリーム中に何のコマンドを
  埋め込む想定か）は**未解明**（呼び出し先の汎用コマンドテーブルを経由するとしか分からず、
  実データにこのパターンが出現するかは未確認）。

**14bitマスクのビット割当**（`pmd_ssgrhythm_opna_table[11]`, `fmdriver_pmd.c:5310-5322`。
reg/data/konの3値の組み合わせ数から、KAJA氏PMD付属ドキュメントで知られる「内蔵SSGリズム
サンプル」の音色バリエーション数と一致することを手がかりに対応付けた）:

| bit | reg | 対応（バリエーション） |
|---|---|---|
| 0 | 0x18 | バスドラム |
| 1 | 0x19 | スネア(1) |
| 2,3,4 | 0x1c | タム(3バリエーション) |
| 5 | 0x1d | リムショット |
| 6 | 0x19 | スネア(2、reg同一・data別) |
| 7 | 0x1b | ハイハット |
| 8,9,10 | 0x1a | シンバル/トップ(3バリエーション) |

reg 0x18-0x1dはYM2608リズム音源の各音源レジスタ（`tools/verify_pmd_rhythm.mjs:9-12`の
コメントで既出）。**この対応表はfmdriver_pmd.cのみから確定**しており、`PMDMML.MAN`側に
バリエーション名の記載は見当たらなかった（`§1-2-1`の例に出る`R0 l16[@64c]4`のような
`@`（音色番号指定、`PMDMML.MAN §6-1-3/6-1-4`）がこの11バリエーションのどれかを指す想定だが、
`@`番号→bit位置の対応規則は**未解明**）。**この意味で「一致」ではなく「fmdriver_pmd.c単独での
確定」であることを明記する**（v1 1.6.1節のような2情報源一致ではない）。

**【step4で解決】** `PMDMML.MAN §6-1-3`（「音色番号指定/SSGリズム定義パート」）を精読した
ところ、`@1`=Bass Drum, `@2`=Snare1, `@4`=Low Tom, `@8`=Middle Tom, `@16`=High Tom,
`@32`=Rim Shot, `@64`=Snare2, `@128`=Hi-Hat Close, `@256`=Hi-Hat Open, `@512`=Crash Cymbal,
`@1024`=Ride Cymbalという対応が明記されていた。これは`1,2,4,8,...,1024`という**2^0〜2^10の
べき乗**であり、上記のfmdriver_pmd.c由来のbit0-10の11エントリ表と**完全に一致**する
（マニュアルの数値そのものが「そのビットを立てた14bitマスク値」になっている）。
よって`@n`（Rパート内の音色番号指定）の`.M`側の意味は「**マスク値そのものをそのまま
14bitマスクとして書き込む**」であり、bit位置への変換テーブルは不要（数値=マスク値）。
2情報源（fmdriver_pmd.cのbit位置表とPMDMML.MANの数値表）が一致したため、この点は解決した。
ただし前述の通り**実データ3曲はこの`@n`方式のRパターン定義を1件も使っておらず**、
実際に必要なのは`\`系コマンド（前掲）の方だったため、実装上の優先度としては下がる。

`§1-2-2`にある`\b\s\c\h\t\i`等（YM2608リズム音源への直接コマンド、`§14`）は
このK/R系統とは**別の経路**（`0xeb`系、`fmdriver_pmd.c:2787-`）であることをv1 1.5節から
再確認した。両者は`pmd_ssgrhythm_opna`フラグの有無で使い分けられている可能性が高いが
（`fmdriver_pmd.c:5388`の条件分岐）、**フラグの設定元（どのMML命令が立てるか）は未解明**。

**【step4で判明・重要】** 実データ3曲の`R`定義行を実際に確認したところ、**3曲とも`@音色番号`
形式のパターン定義は1つも使っておらず、全て`\cr` `\hr%N` `\vh+N` `\vh-N`のような`\`系
直接コマンド（上記の別経路、`§14`）で埋められている**（例: `R1  \hr%13\hr%11 \vh+8 \hr%13
\vh-8 \hr%11`。これは`\h`(ハイハットショット)+`r%13`(休符)+`\h`+`r%11`+`\vh+`(ハイハット
個別音量、相対+8)+... という通常のコマンド列で、`§14`の[音源]欄に`R定義`が明記されている
通り、Rサブストリーム内でも`\`系コマンドがそのまま使える）。よって**実データを実際に
コンパイルするために必要なのは、`@音色番号`による14bitマスク方式ではなく、`\`系コマンドの
バイト実装の方**だと判明した。

`\`系コマンドの`.M`側バイトは今回`fmdriver_pmd.c:2787-2920`を精読し以下を確認した
（マニュアル`§14-1`〜`§14-4`の説明と対応、範囲は一致）:
- `\b\s\c\h\t\i[p]`(ショット/ダンプ) → `0xeb`(`pmd_cmdeb_opnarhythm`)、1byte引数
  （`bit7=1`でダンプ/`0`でショット、下位6bitが対象の音を選ぶビットマスク）。
  **b/s/c/h/t/iの6文字とビット0-5の対応は未解明のまま**（`pmd_opnarhythm_ilpan[6]`配列の
  index順が何の音に対応するかは、この関数のみからは確定できない）。
- `\V[±]`(マスタボリューム、範囲0-63) → 絶対値`0xe8`(`pmd_cmde8_opnarhythm_tl`,
  1byte0-63、マニュアルの範囲と一致)、相対値`0xe6`(`pmd_cmde6_opnarhythm_tl_rel`, 1byte符号付き)。
- `\vX[±]`(個別音量、範囲0-31) → 絶対値`0xea`(`pmd_cmdea_opnarhythm_il`, 1byte:
  上位3bit=対象music番号1-6, 下位5bit=音量0-31、マニュアルの範囲と一致)、
  相対値`0xe5`(`pmd_cmde5_opnarhythm_il_rel`, 2byte: 1byte目=対象番号1-6, 2byte目=符号付き差分)。
- `\lX\mX\rX`(出力位置) → `0xe9`(`pmd_cmde9_opnarhythm_pan`, 1byte: 上位3bit=対象番号1-6,
  下位2bit=l/m/rに対応するパン値)。**l/m/rの3値と下位2bitの数値対応は未解明**
  （`p`コマンドの`pantable[4]={0,9,1,5}`のような対応表が見当たらない）。

上記のうち`\V`(絶対値)は完全に確定できたが、**b/s/c/h/t/iの6音とビット位置の対応**、
**l/m/rとパン値2bitの対応**の2点が未解明のまま残るため、`\`系コマンド全体の実装には
まだブロッカーがある。したがって`K`/`R`本体の実装（1.4節）は今回も見送った。

### 1.4 実装の難易度・依存関係

- `J`(ADPCM): 難易度低。v1のFM/SSGパート実装をほぼそのまま流用でき、新しいヘッダフィールドも
  不要（既存の空きスロットを埋めるだけ）。
- `K`/`R`(リズム): 難易度高。（1）パート文字`K`をトラックとして受理する処理、（2）`R`定義を
  「パート」ではなく「パターン表エントリ」として扱う専用のパーサ/コンパイラ経路、
  （3）`r_offset`フィールドの新規書き込み、（4）14bitマスクのMML側表記(`@`番号との対応、未解明)
  という4つの新機構が要る。**`@`→bitの対応が未解明のままだと、`K`/`R`は「鳴るが音色が
  合っているか検証できない」状態になる**リスクが高い。

## 2. PPZパートの節

SS_TENGは`#PPZfile`/`#PPZExtend`を使う曲（実データで確認: `#PPZfile mspcm3.PZI,mspcm4.PZI`
/ `#PPZExtend abcdef`。ファイル名・拡張子のみの短い断片で、曲固有の情報は含まない）。

### 2.1 パート指定文字は固定ではない

`PMDMML.MAN §2-25`「PPZ8用パート拡張」: `#PPZExtend パート記号1[パート記号2...](8つまで)`、
記号は`LMNOPQSTUVWXYZabcdefghijklmnopqrstuvwxyz`のうち未使用のものをユーザーが選ぶ
（固定のアルファベット割当ではない）。実データ(SS_TENG)は`#PPZExtend abcdef`（6ch、`a`-`f`）。
`fmdriver_pmd.h:29-36`の`PMD_PART_PPZ_1`〜`PMD_PART_PPZ_8`（enum内部値14-21）は
**MML側の文字とは無関係な内部インデックス**であり、`#PPZExtend`で指定された文字の**出現順**が
`PPZ_1`〜`PPZ_8`に対応すると推定される（`PMDMML.MAN §2-25`の例`#PPZExtend abcdefgh`が
「a,b,...,hを新規に拡張しPPZ8パートとする」と書いているのみで、出現順=チャンネル番号順である
ことの明記は無い。**この対応は未解明**、`fmdriver_pmd.c`側のMML文字→enumインデックスの
変換ロジックはコンパイラ内部にあるはずだが、プレイヤー側`fmdriver_pmd.c`だけを見ても
「文字とindexの対応をどこで決めるか」は分からない）。

### 2.2 `.M`側のポインタ格納位置（今回確定）

v1 5章「未解明のまま残った点」にあった「PPZ1-8のデータ先頭ポインタの格納位置」を、
`pmd_cmdb4_ppz8_init`（`fmdriver_pmd.c:4247-4270`）を精読して確定した:

```
0xb4 コマンド（引数16byte固定、cmd_table中の位置はFM/SSG/ADPCM/PPZ8共通表に存在）:
  ptr[0] (2byte LE)  -> PPZ_1のデータ先頭ポインタ（0なら「未使用、スキップ」）
  ptr[1] (2byte LE)  -> PPZ_2
  ...
  ptr[7] (2byte LE)  -> PPZ_8
```

出典: `fmdriver_pmd.c:4253-4260`（`for (i=0;i<8;i++) { ptr=cmdload(); ptr|=cmdload()<<8;
if(!ptr) continue; pmd->parts[PMD_PART_PPZ_1+i].ptr = ptr; ... }`）。

つまりPPZ1-8のポインタは**ヘッダ内の固定フィールドではなく、`0xb4`コマンドの16byte引数**として
どこかのパート（通常は先頭で1回実行される想定、どのパートに置くかはコンパイラの自由）に
埋め込まれる。**この点はv1で「未解明」としていたが、fmdriver_pmd.c単独の読み込みで完全に
解決した**（PMDMML.MANには「`.M`のバイナリ内でどこに置くか」の記載が無いため、
2情報源の突き合わせではなく`fmdriver_pmd.c`単独の確定という位置づけ）。

`pmd_cmdb4_ppz8_init`が呼ばれた時点でその8chの`ptr`/`vol=0x80`/`pan=5`等が初期化される
（`fmdriver_pmd.c:4261-4269`）ため、**PPZ8パートは全パート共通のヘッダポインタ表(1.1節)や
`tone_ptr`の仕組みと独立**しており、`.M`ファイルのどこかに一度`0xb4`を書けば足りる。

### 2.3 音色ファイル(`#PPZfile`)との関係

`PMDMML.MAN §2-26`: `#PPZfile ファイル名1[.PVI/.PZI][,ファイル名2]`。2つ目のファイルを
指定すると音色番号`@128`〜`@255`がそちらに割り当たる。この「音色ファイル自体の読み込み・
バイナリ格納」は`.M`フォーマットの範囲外（別ファイル`.PVI`/`.PZI`の話）であり、
v1が対象外としているADPCM(`PPC`形式)の音色ファイル読み込みと同種の課題。**本書のスコープ外**
のまま次段階へ持ち越す。

### 2.4 実装の難易度・依存関係

`K`/`R`より書式自体は単純（0xb4の16byte引数さえ書ければ良い）だが、**MML文字→PPZチャンネル
番号の対応規則が未解明**なため、`#PPZExtend`のパース自体は可能でも、正しいチャンネルへの
ポインタ書き込みは検証できない。また`#PPZfile`（別ファイル読み込み）に触れない限り
実際の音は鳴らせない（ADPCMと同じ制約）。**実務上の優先度は低い**（実データで1曲のみ必要）。

## 3. 文字ごとの節

### 3.1 `(` / `)` — 音量相対変化

出典: `PMDMML.MAN §5-5`「音量相対変化」。書式 `) [^] [%] [数値]` / `( [^] [%] [数値]`、
範囲0-255、数値省略時は1。`)`=加算、`(`=減算。`%`付きで細かい値(Vコマンド相当)、
無しで大雑把な値(vコマンド相当、**指定数値の4倍**とFM音源では明記)。`^`は次の1音だけに
効果を限定する（アクセント）。

`.M`側は**2つの独立したコマンドが存在**（`fmdriver_pmd.c`のcmd_table、FM用）:
- `0xf4`(`pmd_cmdf4_volinc_fm`, `:2526-2534`): **引数0byte**、`part->vol += 4`固定。
- `0xf3`(`pmd_cmdf3_voldec_fm`, `:2562-2570`): **引数0byte**、`part->vol -= 4`固定。
- `0xe3`(`pmd_cmde3_vol_add_fm`, `:2920-2928`): **引数1byte**、`part->vol += 引数`。
- `0xe2`(`pmd_cmde2_vol_sub`, `:2958-2966`）: **引数1byte**、`part->vol -= 引数`。

**両情報源は一致した**: `)`(引数省略・%無し)の効果はFMで「4倍」=4、これは`0xf4`の固定+4と
数値的に一致する。よって`)`/`(`は「数値省略・%無し・^無し」の場合に限り`0xf4`/`0xf3`
（0byte、コンパクト）でも`0xe3`/`0xe2`（1byte引数=4）でも**runtime上は同じ結果**になる。
どちらを実際に選ぶかはコンパイラの自由（MC.EXEがどちらを選ぶかは未確認、本コンパイラは
実装を統一しやすい`0xe3`/`0xe2`（常に1byte引数、%指定時は引数=数値そのもの、%無し指定時は
引数=数値×4）に一本化する設計で問題ない）。

**未解明**: `^`（アクセント、次の1音だけに限定）に対応する専用の実行時フラグやビットは、
`fmdriver_pmd.c`のこの周辺のコマンド（`0xf4/0xf3/0xe3/0xe2`のいずれの引数にもそれらしい
ビット処理は見当たらなかった）には見つからなかった。**コンパイル時に「加算コマンド→対象の
1音→直後に同量の減算コマンド」という3つの命令列へ機械的に展開する**（ランタイム支援なしで
実現できる）という可能性が高いと推測されるが、これは推測であり実装前に要検証。

依存関係: 音量コマンド(`v`/`V`、v1実装済み)の値域チェックロジックを再利用できる。

### 3.2 `p` — パン設定1

出典: `PMDMML.MAN §13-1`。書式`p 数値`、範囲0-3（FM(OPNA,OPM)/PCM共通、意味は音源種別で
1と2が入れ替わる: OPNAは1=右2=左、OPMは1=左2=右、3=中央固定）。

`.M`側: `0xec`(`pmd_cmdec_pan`, `fmdriver_pmd.c:2737-2743`)。**引数1byte、値をそのまま

「1byteそのまま」であることは確定）。

**両情報源は一致**: マニュアルの範囲(0-3)と、コード側が単純に1byte引数を読むだけという
シンプルさが整合する（複雑な変換を要するなら範囲が0-3という綺麗な数字にならない）。

難易度: 低。値域チェック(0-3)だけで実装できる。他コマンドへの依存なし。

**関連（今回未対応、参考として記録）**: `px`（§13-2、2byte引数、より細かいパン+逆相指定、

FM側では使われていない=定数扱い）。実データ3曲での出現は未確認（今回は`p`のみが集計対象）。

### 3.3 `q` — 音の切り方の指定2

出典: `PMDMML.MAN §4-13`。書式`q [数値1][-[数値2]] [,数値3]`（`l音長`形式もあり）。
- 数値1: 基本の後ろカット量。
- 数値2: 指定時、数値1〜数値2の範囲でランダムに後ろカット。
- 数値3: 最低保証の発音長（これより短くならない）。

`.M`側で対応が**部分的に**特定できた（FM用cmd_table内、`fmdriver_pmd.c:1461-1493`
`pmd_part_calc_gate`の実装から逆算）:
- **数値3 → `0xb3`(`pmd_cmdb3_gate_min`, `:4276-4284`)**。引数1byte、`part->gate_min`。
  `gate_min`が非0のとき`len_cnt - gate_min`未満にはならないようクランプする処理
  (`:1485-1491`)が、マニュアルの「数値3 = 最低でもこの長さは発音」の説明と**完全に一致**。
- **数値2 → `0xb1`(`pmd_cmdb1_gate_rand_range`, `:4296-4304`)**。引数1byte、
  `part->gate_rand_range`。bit7を符号（1なら減算方向）、下位7bitを乱数の範囲として使う
  (`:1473-1483`)。マニュアルの「数値1〜数値2の範囲でランダムに後ろから切る」の**ランダム性・
  方向という2つの性質が一致**。
- **数値1 → `0xfe`(`pmd_cmdfe_gate_abs`)【2026-08-18 参照.M実測で解消】**。
  `tools/pmd-reference/pmdq1b.mml`(MC.EXE ver4.8s実測)で確定: `q45`単体は
  `fe 2d`(=45そのまま1byte)、`q78,12`は`fe 4e b3 0c`と、**Q(大文字)との合成は無く、
  数値1をそのまま1byte書くだけ**だった。以前候補に挙げていた`0xc4`(gate_rel)は
  q数値1とは無関係で別コマンド(おそらくQ大文字側、本コンパイラでは引き続き未実装)
  だったとみられる——`Q3 q45`のように大文字Qを併用すると`0xc4 a0`が別途先頭に
  現れることを確認したため(pmdmp/pmdq1系のcorpus初版で発見、最終版では大文字Qを
  使わない形に整理)。
  **副産物として数値2(`0xb1`)側の仕様誤りも発見**: 数値1が明示されているとき、
  `0xb1`下位7bitは「数値2そのもの」ではなく**`|数値1-数値2|`の差分**で、bit7(方向)も
  固定ではなく**符号で決まる**(数値2<数値1で1、数値2>数値1で0)。`q50-30,15`→
  `fe 32 b1 94`(=0x80|20=|50-30|)、`q30-90,2`→`fe 1e b1 3c`(=0|60=|30-90|、bit7=0)の
  両方向を実測して確認した(`compiler/pmd_mml_parser.mjs`の`q`ハンドラに実装、
  数値1が一度もそのパートで明示されていない場合は旧来どおり数値2をそのままbit7=1固定
  で書く後方互換パスを残している——後述の`pmdgate.mml`の未解明点のため)。
  **新たな未解明点**: 既存corpus`pmdgate.mml`(`q-10,5`のように数値1を一度も明示しない
  形)の参照.Mを見ると、パート先頭に説明のつかない`fe 01`が現れ、後続の`0xb1`の値も
  「数値2そのもの」ではなく「`|1-数値2|`」のように見える(`q-10,5`→`b1 09`=|1-10|、
  ただし2つ目の`q-20`→`b1 14`=20そのままで一貫しない)。数値1を一度も指定しない場合の
  既定値・保持規則は依然**未解明**のまま(`pmdgate.mml`のbaselineは変更していない)。

難易度: 低〜中（数値1〜3とも実装済み。数値1を一度も明示しない場合のQとの相互作用のみ
未解明として残存——上記参照）。

### 3.4 `!` — MML変数定義・使用

出典: `PMDMML.MAN §3-2`（定義）・`§16-1`（使用）。`!文字列 MML文字列` または `!数値 MML文字列`
で変数を定義し、本文中で`!文字列`または`!数値`と書くとその場に定義済みMML文字列が
**展開**される（最大256種×2、文字列は先頭30文字まで判別、再帰は禁止だがネストは可能、
最長一致で変数名を検索する等の細かい規則あり）。

`.M`側の出力バイト列: **無し**。これは`.M`バイナリのコマンドではなく、**コンパイラの
プリプロセス（テキスト置換）段階でのみ意味を持つMML側の機能**であり、展開後のMML文字列が
最終的に生成する`.M`バイトは、展開先のコマンド自体（音符・音色選択等）がすでにv1/本書で
定義済みのものと同一になる。**この点は`fmdriver_pmd.c`側に対応するコマンドが存在しない
ことと整合しており（読了範囲に`!`用のコマンドは見当たらない）、2情報源の「一致」ではなく
「`.M`レベルでは非該当」という結論**。

**【step4で実装】** `PMDMML.MAN §3-2`/`§16-1`をWebFetchで再取得・精読し、以下の規則を
マニュアル記述から一次情報として確定させた（fmdriver_pmd.cとの突き合わせは不要、
コンパイラのプリプロセス機能のためマニュアル単独で確定できる）:
- 定義名は「先頭が数字でなければ任意の文字種」（文字列名）または純粋な数値（0-255）。
  本実装ではマッチング処理上この2種を区別する必要が無いため、1つの名前空間として扱う
  （数値名も文字列としてそのまま前方一致検索に使える）。
- 使用時は`!`の直後から、定義済み変数名のうち**最長一致するもの**を採用する
  （`§16-1`注意1「!bcc!bc!bの順に検索」の例で確認）。
- 値のネストは可能（値の中に別の`!変数`を含められる）。再帰は「絶対にしないでください」と
  警告があるのみで具体的な検出方法の記載は無いため、無限ループを避ける安全側の実装判断として
  本実装は再帰を検出したら`ParseError`にする（マニュアルの規定そのものではなく実装判断）。
- 重複定義（同名を複数回`!`定義した場合にどちらが有効か）は`PMDMML.MAN`に明記が無く**未解明**
  のまま。実データ3曲では重複定義は出現しなかった（目視確認）。本実装は他の重複コマンド
  （`#Title`等、v1 8.1節）と同じ「後勝ち」を暫定的に採用しているが、これは推測であり実測で
  裏付けたものではない。
`compiler/pmd_mml_parser.mjs`にプリプロセス関数(`collectVariableDefs`/`expandVariables`)を
追加し、各パート本文の字句解析直前に展開するよう実装した。検査は
`tools/verify_pmd_mml_v2_commands.mjs`の9番セクション（`§3-2`例1の再現、`§16-1`例1の
最長一致再現、再帰検出、陽性対照）で行った。

難易度: 中（バイト列は不要だが、コンパイラのプリプロセッサとして文字列/数値2種の変数表・
最長一致検索・再帰検出を実装する必要があり、パーサの構造変更を伴う）。依存: 他のどの
コマンドにも先行して展開を終える必要がある（展開後のテキストに対して通常のトークナイズを行う）。

### 3.5 `{` `}` — ポルタメント指定

出典: `PMDMML.MAN §4-3`。書式`{音程1 音程2} [音長1][.][,音長2]`。音程1から音程2へ滑らかに
繋げる。音長2(ディレイ)指定時は「発音開始から音程が移動するまでの待機」。対象音源は
FM/SSG/PCM(AD,PPZ)。Rパートでは不可。`{ }`内には`c d e f g a b o > <`のみ許可。

`.M`側: v1 1.4節の「それ以外(`0xf2`〜`0xb1`)」に一括りにされていた範囲の中に
`pmd_cmdda_portamento_fm`(`0xda`, `fmdriver_pmd.c`内、cmd_table_fmの並びから位置を確認)が
ある。**今回は関数名の存在確認のみに留め、引数の個数・バイトレイアウトまでは精読していない
（未解明）**。理由: `{ }`は「2つの音程＋2つの音長」という他の音符コマンドより複雑な構造を
持ち、`.M`側の1コマンドにどう収まっているか（音程2つを両方1byteずつ積むのか、差分値なのか等）
を確定するには`pmd_cmdda_portamento_fm`本体の精読が別途必要。次段階の課題とする。

**【step4で解決・実装】** `fmdriver_pmd.c:3083-3121`（`pmd_cmdda_portamento_fm`）を精読し、
引数構成を確定した:
```
note1 = pmd_part_cmdload(...)   // 通常の音符バイトと同一形式(1byte、noteByte(octave,idx))
note2 = pmd_part_cmdload(...)   // 同上
clocks = pmd_part_cmdload(...)  // part->len=part->len_cnt=clocks(通常の音長クロックと同じ)
```
すなわち`0xda`の引数は**3byte固定**（note1, note2, clocks）で、SSG/ADPCM/PPZ8版
（`pmd_cmdda_portamento_ssg/_adpcm/_ppz8`, いずれも同じ`pmd_cmdda_*`という命名かつ各パート種の
cmd_table中で同じ`0xda`インデックスに配置されている）も同型の3引数読み込みだった
（PPZ8版のみ周波数が32bit拡張だが引数の個数・意味は同じ）。

マニュアルの書式`{音程1 音程2} [音長1][.][,音長2]`にある**音長2（ディレイ）は`.M`側に
専用フィールドが無い**。`PMDMML.MAN §4-3`の例2「`{cg}4,8` は `c8&{cg}8` と同様になります」
という一次情報の記述をそのままコンパイル規則として採用した: 音長2(delay)が指定された場合、
「note1のピッチをdelayクロックぶん発音してtie(`&`, `0xfb`)で繋ぎ、残り
(音長1クロック − delayクロック)ぶんをポルタメント本体(`0xda`)にする」という**3命令
(note+tie+portamento)への展開**をコンパイル時に行う。音長2は音長1より短い値である必要が
あるという範囲制約（`PMDMML.MAN §4-3`[範囲]）も、この展開規則で残りクロックが1以上になる
ことの必要条件として自然に一致する。

`{ }`内は`c d e f g a b o > <`のみ許可（`PMDMML.MAN §4-3`）で、内部の`o`/`</>`は
パート共通のオクターブレジスタを更新するため`}`の外まで持ち越される（通常の音符と同じ扱い）。

これにより、コード（引数バイト数の直接読み取り）とマニュアル（ディレイの意味・例の数値）の
**独立した2情報源が一致**し、v1 1.4節/本節の「未解明」は解消した。`compiler/pmd_mml_parser.mjs`
にポルタメント本体を実装、`compiler/pmd_mml_compiler.mjs`に`portamento`イベント
（0xda+3byte）を追加した。検査は`tools/verify_pmd_mml_v2_commands.mjs`の11番セクション
（基本形・ディレイ展開・許可文字外エラー・陽性対照）で行った。

難易度: 高だったが今回解決。依存: 音符・音長のクロック計算（v1で確立済み）をそのまま流用。

### 3.6 `M` `MA` `MB` — ソフトウエアLFO指定

出典: `PMDMML.MAN §9-1`。`M`/`MA`=LFO1、`MB`=LFO2。書式は「delayのみ」または
「delay(またはl音長), speed, depthA, depthB」の4値。範囲: delay/speed/depthB=0-255、
depthA(数値3)=-128〜+127。

`.M`側: `0xf2`(`pmd_cmdf2_lfo`, `fmdriver_pmd.c:2599-2610`)。**引数は常に4byte固定**
（`delay, speed, step(depthA), times(depthB)`の順に`pmd_part_cmdload`を4回呼ぶだけ、
条件分岐は無い）。LFO2用は`0xbf`(`pmd_cmdbf_lfo2`, `:4028-4035`)で、中身は`pmd_cmdf2_lfo`を
そのまま呼ぶラッパー（同一バイト書式）。

**両情報源は一致**: マニュアルの4パラメータ(delay/speed/depthA/depthB)と、コードが
`cmdload()`を4回呼ぶ実装が1:1対応する。「delayのみ単独指定」というMML側の省略形は、
**`.M`側には省略形が存在しない**（常に4byte）ため、コンパイラが「直前に指定されたspeed/
depthA/depthBの値を保持し、delay省略時にそれらを埋めて4byte全部を書き出す」という**状態保持**
を実装する必要がある。これは推測ではなく、`0xf2`が無条件に4byte読む実装から**論理的に導かれる
コンパイラ側の必須要件**である。

**【step4で解決・実装】** `PMDMML.MAN §9-1`を再度精読したところ、「delayのみ単独で指定すると、
現在のdelay値のみ変更します」という一文が明記されていた。これは上記のコード側からの論理的
推論（状態保持が必須）と**完全に一致**し、「delay省略形＝直前のspeed/depthA/depthBを保持し
delayだけ差し替えて4byte全部を再送出する」という規則が2情報源(コードの4byte固定読み込み +
マニュアルの明文規定)で確定した。パート内で最初の`M`がdelay単独形の場合（保持すべき値が
存在しない）はエラーとする。`compiler/pmd_mml_parser.mjs`に`state.lfoParams`（直前の
speed/depthA/depthB）を追加して実装した。検査は`tools/verify_pmd_mml_v2_commands.mjs`の
10番セクション（保持の再現・陽性対照・初回delay単独のエラー化）で行った。

難易度: 中（今回解決）。依存: LFOの深さ変化(`§9-7`)・LFO波形(`MW`, `§9-2`)等、`M`単体では
音として完結しない周辺コマンド群がある（今回も`M`自体の書式確定のみ、波形/深さ変化は
引き続き範囲外）。

**【2026-08-18 追記】`MA`/`MB`(LFO2選択)と`MP`/`MPA`/`MPB`を実装**。実データ3曲(第三者MML、
リポジトリ非同梱)を調べたところ、「M書式バリエーション」に見えていたエラーの**実体は
ほぼ全てMP/MPA/MPB**だった(通常のM 4値形・delay単独省略形は実データ上0件で、既に完全対応
済みだった)。`MP`/`MPA`/`MPB`(上昇/下降専用LFO指定)は`PMDMML.MAN §9-6`が出典で、
「`MP ±数値1[,数値2[,数値3]]` は `MA(またはMB) 数値2,数値3,数値1,255` と同じで、LFOをONに
します」と明記されている。参照.M実測(`tools/pmd-reference/pmdmp.mml`、MC.EXE ver4.8s)で、
`MP-77`→`f2 00 01 b3 ff f1 01`(0xf2=delay0,speed1,depthA=-77,depthB=255固定 →
0xf1=LFOスイッチに固定値1)、`MPB39`→`bf 00 01 27 ff be 01`(LFO2側は0xbf/0xbe)と、
マニュアルの説明どおり「M本体+LFOスイッチON(固定値1=音程+同期)」の2コマンド構成である
ことをbit単位で確定できた。`lfoBody`/`lfoSwitch`イベントに`lfo`(1|2)フィールドを追加し、
LFO2は`0xbf`/`0xbe`へ振り分ける形で実装した(`compiler/pmd_mml_compiler.mjs`)。

### 3.7 `*` `*A` `*B` — ソフトウエアLFOスイッチ

出典: `PMDMML.MAN §9-3`。書式`* 数値1[,数値2]`（`*A`/`*B`で対象を明示）。範囲0-7
（bit0=音程LFO on、bit1=音量LFO on、bit2=keyon非同期、の3bit構成とマニュアルの表から
逆算できる）。

`.M`側: `0xf1`(`pmd_cmdf1_lfo_switch_fm`→`pmd_cmdf1_lfo_switch`, `fmdriver_pmd.c:2513-2536`)。
**引数1byte**。`val & 0xf8`が真なら`val=1`に強制（安全側クランプ、マニュアルの0-7範囲より
広い入力への防御）。`freq=val&1, vol=val&2, sync=val&4`という**ビット分解が、マニュアルの
数値表（1=音程+同期, 2=音量+同期, 4=off, 5=音程+非同期, 6=音量+非同期）と全項目で一致**した
（例えば数値=4は「sync bitのみ立つがfreq/volが両方0なので聴感上0と区別つかない」ことも、
マニュアルが4を明示的に「off」と書いていることと整合する）。LFO2用は`0xbe`
(`pmd_cmdbe_lfo2_switch_fm`)。

**両情報源が完全一致**した数少ない項目の一つ。難易度: 低。依存: `M`(§3.6)で設定した
LFOパラメータが無いと聴感上の効果が出ない（`*`単体は「有効/無効の切り替え」のみ）。

### 3.8 `C` — 全音符長の設定

`PMDMML.MAN §4-11`。書式`C 数値`（範囲1-255）。実データでの出現形は`C106`/`C192`/`C108`
（全音符長は96の倍数で使うのが典型、192は「64分音符まで使いたい場合」の例として
マニュアルにも`C192`という同じ数値が例示されている）。全パートで共通のグローバル設定
（「いずれかのパートの頭に設定すれば、すべてのパートに有効」）。

**なぜ現状「未対応の文字」としてエラーになるか**: `compiler/pmd_mml_parser.mjs`の
`NOTE_LETTER_TO_BASE_INDEX`（`:22`）は音名を**小文字のみ**(`c,d,e,f,g,a,b`)で登録しており、
大文字`C`はこのテーブルにヒットしない。さらに`tokenizeBody`内には大文字`C`を処理する
専用分岐も存在しない（`O`(oと共用)/`L`/`T`/`V`は専用分岐があるが`C`には無い）ため、
最終的に`:271`の「未対応の文字です」に落ちる。**これは実装漏れであり、`C`が音名の大文字表記
として使われているわけではない**——`PMDMML.MAN §4-1`の音符表記は`c/d/e/f/g/a/b`と
小文字のみで説明されており、大文字`C`はここでは**別のコマンド（全音符長設定）**である。
実データの出現形(`C106`,`C192`,`C108`)も、続く数値が音符長の典型的な倍数(96の倍数)である
ことから、音名ではなく全音符長設定コマンドとして使われていることと整合する。

`.M`側: v1 1.3節で「未解明」としていた`0xdf`(`pmd_cmddf_meas_len`, `fmdriver_pmd.c:3001-3008`)
を、今回**確定できた**。根拠:
1. `pmd->meas_len`(グローバル変数、`part->`ではなく`pmd->`)であり、**パートに依らず全体で
   共有される**。これは`PMDMML.MAN §4-11`の「いずれかのパートの頭に設定すれば、すべての
   パートに有効となります」という説明と**一致**する。
2. v1 1.3節で候補に挙がっていたもう一方の`Z`（`PMDMML.MAN §15-8`「小節の長さ設定」、
   デフォルト96という共通点だけで区別できずにいた）は、マニュアルに**「演奏には全く影響は
   ありません」**と明記されている（ゲーム側が小節番号を取得するためだけの外部向けメタ情報）。
   `0xdf`の`meas_len`は音長→クロック変換の分母として実際に演奏へ影響するため、**Zとは
   一致し得ない**。この消去法により`0xdf`=Cで確定した。

これによりv1 5章の「未解明」（`0xdf`がCかWのどちらか）は**解消**とする。

難易度: 低（1byte引数、値域チェックのみ）。依存: 既存の音長計算ロジック（96固定の除数計算）
を「Cで指定された値」に一般化する必要がある（v1は96固定を前提にしていたため、音長計算部分の
改修を伴う。実装上のインパクトはこの一点のみ）。

### 3.9 `D` — デチューン設定

`PMDMML.MAN §7-1`。書式`D 数値`(絶対)/`DD 数値`(相対)、範囲-32768〜+32767。
実データ出現形: `D1`/`D2`/`D3`/`D5`。

**なぜエラーになるか**: `C`と同じ理由。小文字音名テーブルに`D`は無く、大文字`D`用の専用分岐も
無いため未対応文字扱いになる。`D`もまた音名の大文字表記ではなく、独立したデチューンコマンド
（`c`とセットで「パート行頭のC/D」＝FM3/FM4という**別の意味**でも`C`/`D`が使われる
（1章参照）ため紛らわしいが、**行頭のパート指定文字と、本文中のコマンド文字は別レイヤー**
であり、両立して問題ない（`PMDMML.MAN §1-1-2`の失敗例が示す通り、パート指定文字とMML本文の
間には必ずスペース/タブが必要なため構文上も曖昧さは無い）。

`.M`側: v1 1.4節で既に`0xfa`(`pmd_cmdfa_det`, `fmdriver_pmd.c:2410-2419`。2byte LE符号付き)
として特定済み（絶対値=`D`）。相対値=`DD`は今回追加確認: `0xd5`
(`pmd_cmdd5_detrel`, `:2422-2431`)、同じく2byte LE符号付きで`part->detune +=`する点のみ`D`と
異なる。**両情報源は一致**（マニュアルの-32768〜+32767という16bit符号付きレンジと、コードの
2byte読み込みが対応）。

難易度: 低。依存: 無し（音符コマンドとは独立に動作する）。

### 3.12 `_` / `__` — 転調指定（今回新規に発見・解決、実データで`!`展開後に必須と判明）

`!`（3.4節）の実装後、実データ3曲すべてで使われている`!H`変数の展開先が`_0`（例:
`!H _0`）であることが分かった。他にも音色マクロの中に`_4`・`_-1`のような表記が
頻出する（例: `!o @31 v8 o5p1_4`）。`_`自体は本書v2の当初スコープに無かったが、
`!`実装の効果を実際に引き出すために解決を試みた。

出典: `PMDMML.MAN §4-14`。書式`_ +数値` / `_ -数値`（絶対）、`__ +数値` / `__ -数値`（相対）、
範囲-128〜127。実データの`_0`のように符号が省略された表記もあるため、本実装は符号省略時を
正数として寛容に受理する（マニュアルの書式は符号必須だが、実データとの整合を優先した実装判断）。

`.M`側: `fmdriver_pmd.c:2516-2523`(`pmd_cmdf5_transpose`, `0xf5`)が絶対値、`:2864-2871`
(`pmd_cmde7_transpose_rel`, `0xe7`)が相対値。いずれも`pmd_part_cmdload`を1回呼ぶだけの
**1byte符号付き引数**。**両情報源が一致**（マニュアルの-128〜127という8bit符号付きレンジと、
コードの1byte読み込みが対応）。

難易度: 低。依存: 無し。`compiler/pmd_mml_parser.mjs`/`compiler/pmd_mml_compiler.mjs`に実装、
検査は`tools/verify_pmd_mml_v2_commands.mjs`の12番セクションで行った。

### 3.10 オクターブ範囲外

`PMDMML.MAN §4-4`は`o`コマンドの範囲を「1〜8」(FM/SSG)とし、デフォルト4とする。v1
6.3節はこれを「実バイト値のnibbleは0-7、o1〜o8という表記は俗称」と解釈し、`o`/`<`/`>`いずれも
0-7の範囲チェックを実装済み。今回、実データ3曲を通した結果、**明示的な`o`数値は最大でも
o1〜o6の範囲**（3曲とも実測: o1,o2,o3,o4,o5,o6のみ出現、o7/o8は無し）だったにもかかわらず、
**`<`/`>`の連続適用によって2曲でオクターブ8〜10相当のエラーが出た**。

**原因の切り分け（今回の調査で判明）**: エラーが出た`I`パート（SSGパート3）の行を実データ上で
遡ると、エラー直前の行が**`(`（今回未対応の文字、§3.1参照）で始まっていた**
（例: `I    (([<bge<b>>]2)) p2[ee<e(4e)4>]2 ...`）。現在のパーサ(`tokenizeBody`)は
1行の途中で未対応文字に遭遇すると`ParseError`を送出してその行の残りのトークンを
**一切処理せず**に次の行へ進む（`compiler/pmd_mml_parser.mjs:477-490`のcatch節）。
その行に含まれていた`<`/`>`（オクターブ変化）は**行の途中の`(`より後にあるものも前にあるものも
含め、その行全体が丸ごとスキップされる**ため、パート内で本来蓄積されるはずのオクターブ状態が
反映されない。

これにより、**後続の行のオクターブ状態が、実際にPMDが解釈するはずの値からずれる**。
今回エラーが出た行(`I    <<a>ceg ...`)の直前行が丸ごとスキップされていたことを実データ上で
確認した。**この「オクターブ範囲外」エラーは、`(` `)` `p` `q` `!` `{` `M` `*` 等の未対応文字が
先に同じパート内の別行に出現し、その行のオクターブ変化コマンドが失われたことの**副作用**である
可能性が高い**——実際のPMD MMLとして`o`が0-7(または1-8)を逸脱した記述をしているとは
断定できない。

**未解明として残す**: 3.1〜3.9節の未対応文字がすべて実装され、パーサが「1行の途中で未対応文字に
遭遇しても、認識できた範囲までの状態変化は保持しつつエラーだけ記録する」設計（あるいは全ての
対応する文字が実装されて行が最後まで解釈できる状態）になった後で、**改めてオクターブ範囲外が
再現するかどうかを検証しないと、これが独立した課題なのか、他項目の未実装から生じる見かけ上の
現象なのかは確定できない**。

難易度・依存関係: **単体では評価不能**。3.1(`(``)`)・3.2(`p`)・3.3(`q`)・3.4(`!`)・3.5(`{`)・
3.6(`M`)・3.7(`*`)がすべて実装された後に再測定することを推奨する（実装順の項でも
最後に置く理由）。

**【step4で再測定・部分的に解消】** `!`/`{ }`/`M`のdelay省略形/`_`を実装した後、実データ3曲を
再度通したところ、オクターブ範囲外エラーはJSM 8→9件、YD 4件（変化無し）、SS_TENG 0→1件と
**むしろ微増**した。原因を実データで確認したところ、すべて「その行に`q`の数値1単独指定
（3.3節、未解明のため今回も未対応）や`K`/`R`リズムパート（1.3節、未実装）など、
**依然として未解決の別要因**が同じ行/同じパートの別行に残っており、それによる行スキップの
副作用で後続行のオクターブ状態がずれている」ケースだった（3.1〜3.7実装前は`!`や`{`自体で
先に行が落ちていたため見えていなかった別の未解決要因が、`!`/`{`解消後に相対的に前面に
出てきた形）。よって**「未解明」という結論自体は変わらない**——`q`数値1・`K`/`R`が
未解決である限り、この項目は依然として独立評価できない。

### 3.11 `@n`の複数回定義

実データ3曲すべてで、同じ音色番号が複数回定義される箇所が見つかった（例:
`@181`がYDで3回、`@174`がSS_TENGで3回、`@249`がJSMで2回。いずれもALG/FBの数値は各回で
同一で、オペレータ4行の一部数値のみ異なっていた——具体的な数値差分は曲データの詳細に
立ち入るため本書には転記しない）。

`PMDMML.MAN §3-1`には「同じ音色番号を複数回定義した場合にどうなるか」の明記が**見当たらな
かった**（`[備考]`で触れているのは`=音色名`の任意位置表記のみ）。`§2`全般注記の
「`#Memo`以外のコマンドを重複指定した場合は、後ろの行にあるものが有効」（v1 8.1節で
`#Title`等に適用した規則）が`@`音色定義にも及ぶかどうかは、この注記が「`#`で始まる全体設定
コマンド」章(`§2`)の中の記載であり、`@`音色定義は別章(`§3`)にあるため**適用範囲が不明**。

`fmdriver_pmd.c`側は`pmd_get_toneptr`(`fmdriver_pmd.c:999-1013`、v1 1.6節で既出)が
**`tone_ptr`から前方へ線形探索し、最初に一致したエントリを採用する**(`:1006-1008`、
ループは`toneptr += 0x1a`で単調に進み、`data[toneptr]==tonenum`で即returnする)。
これは「**同じ音色番号を複数回書いた場合、ファイル内で先に置かれた定義が常に使われ、
後から書いた定義は再生側からは到達不能（無効データ）になる**」ことを意味する。

**未解明**: 上記はあくまで**再生側（`.M`を読む側）の挙動**であり、**コンパイル側（MC.EXE等が
`.M`を書き出す際、同じ音色番号の複数回定義をどう扱うか）は別問題**。考えられる可能性は
少なくとも3つある: (a) MC.EXEが単純にすべてのMML中の`@`定義をそのままの順で`.M`へ出力し、
結果として2つ目以降は`pmd_get_toneptr`の線形探索で無視される（＝後の定義は事実上無効。
実データの曲がこれを意図していないなら**作者側の見落とし/慣習的な冗長記述**の可能性がある）、
(b) MC.EXEが同じ番号のエントリを**上書き/デデュープ**して1つだけ`.M`へ書き出す（＝後の定義が
勝つ、`fmdriver_pmd.c`のコード上は区別できない）、(c) `@`の直後に音符が続く場合、これは
「音色の再定義」ではなく「一時的なパラメータ変更（別の意味を持つ構文）」で、実は**音色番号の
再利用ではない**（`PMDMML.MAN §3-1`の書式を読む限りこの可能性は薄いが、完全には排除できない）。
`fmdriver_pmd.c`だけでは(a)/(b)の判定ができず（両者とも最終的な`.M`バイト列が異なるだけで、
読み出し側のコードは同じロジックで動く）、**MC.EXEのソース（本タスクでは参照方針外）が
無いと確定できない**。

v1の既存実装（`compiler/pmd_mml_parser.mjs:427-447`）は複数回定義を**即エラー**にしている。
これは(a)(b)どちらであっても「曖昧な`.M`を静かに生成しない」という安全側の選択として
妥当ではあるが、**実データの3曲すべてがこの構文を使っている以上、v1のまま「エラーで拒否」を
続けると実データが1曲もコンパイルできない**。

**【step2で実測・解消】** 実データ3曲の参照`.M`ファイルと突き合わせて実測した（測定方法:
自作パーサで音色定義ブロックを全件収集し、同一音色番号の「最初の定義」と「最後の定義」を
それぞれ`buildToneEntry()`で26byteへ組み立て、参照`.M`のtone_ptr以降を26byte単位で走査して
得た同一音色番号のエントリと突き合わせた）。結果: **比較できた5件（JSM `@249`、YD `@145`・
`@101`、SS_TENG `@220`。3曲合計6件の重複のうち、参照側から該当エントリを見つけられた5件）
すべてで「最後の定義」が完全一致し、「最初の定義」はいずれも不一致だった**。よって
**「後勝ち」（(b)、後の定義が有効）を採用する**。

ただしこの測定には2点の留保がある:
1. **26byteの音色テーブル比較には、今回のタスク範囲外の既存バグの補正が必要だった**。
   単一定義（重複なし）の音色ですら、素の`buildToneEntry()`出力は参照`.M`と一致しなかった
   ——原因は**オペレータの並び順**で、DT1/MUL/TL/KS-AR/AM-D1R/D2R/SL-RRの各フィールドで
   「2番目のオペレータ行」と「3番目のオペレータ行」を入れ替えると単一定義の音色が
   全件（JSM 7/7、YD 6/7）一致することを確認した（YM2608系でよくある物理スロット順
   1,3,2,4の可能性が高いが、この配線バグ自体の確定・修正は本書のスコープ外——`@n`複数回
   定義とは無関係な既存の音色テーブルエンコード側の問題であり、次段階の課題として切り出す）。
   上記の「後勝ち」判定はこのスワップ補正を適用した上での比較であり、素のバイト列同士では
   （オペレータ順バグに埋もれて）判定できない。
2. YD`@181`（3回定義）は上記のスワップ補正を適用しても3回の定義いずれも参照`.M`の該当
   エントリと一致しなかった。参照`.M`側を走査すると、同一音色番号(`@181`や`@67`)が
   tone_ptr以降に**複数回出現**しており（例: `@181`が2箇所、`@67`が2箇所、さらに
   `tonenum=0`という不審なエントリも1件）、単純な「tone_ptrからEOFまでを26byte単位で
   走査する」という本測定の抽出方法がテーブル終端付近で境界を誤っている可能性が高い
   （本コンパイラの出力レイアウトはtone_ptr以降が音色テーブルのみで終端=EOFだが、
   参照`.M`側が同じ前提とは限らない）。この1件は**比較不能のまま未解明で残す**。

結論として、5/5(比較できた全件)が一致する強い実測結果に基づき「後勝ち」を採用したが、
「オペレータ並び順バグの補正」という一段階の仮定を経由した間接測定であること、
および1件（`@181`）は抽出手法の限界で判定できなかったことを明記する。

難易度: 低（実装自体は「後勝ち」でエントリを上書きするだけ）。依存: 無し。実装済み
（`compiler/pmd_mml_parser.mjs`の`@`定義ブロック処理、`tones.set(tone.tonenum, tone)`で
常に上書きする形に変更した）。

## 4. 実装順の提案

判断基準は「（a）影響曲数が多い／（b）依存が少なく単体で完結する／（c）未解明が実装を
ブロックしない」の3つ。

1. **`@n`複数回定義の「後勝ち」許容**（3曲全部に影響、実装コストは最小、依存無し）。
   これが無いと実データが1曲もコンパイルできないため、他のどの項目よりも先に着手する
   価値が高い。未解明（MC.EXEとの一致は未確証）はあるが、実装のブロッカーにはならない。
2. **`C`（全音符長）・`D`（デチューン絶対値/相対値）**（3曲中それぞれ実質3曲・3曲相当で影響大、
   両情報源が完全一致し未解明が無い、既存の音長計算ロジックの一般化で対応でき依存も小さい）。
3. **`p`（パン）・`*`（LFOスイッチ）**（両情報源が完全一致、実装コストが低い、`*`は`M`より先に
   スイッチのon/off自体は実装できる）。
4. **`( )`（音量相対変化）・`M`（LFO本体）**（基本形は情報源一致で実装可能、`^`アクセントと
   `M`の省略形保持だけ後回しにできる部分実装が可能）。
5. **`J`（ADPCMパート）**（2曲に影響、FM/SSGの実装をほぼ転用できるため単体で完結）。
6. **`q`（ゲート時間2）**（3曲に影響し優先度は本来高いが、数値1のバイト表現が未解明のため
   数値2/3のみ先行実装し、数値1はQとの合成ロジックが確定してから追加する2段階が必要）。
7. **`!`（MML変数）**（影響は間接的だが、パーサのプリプロセス層を丸ごと新設する必要があり
   構造変更が大きいため、他のコマンド実装が一通り落ち着いてから着手する方が手戻りが少ない）。
8. **`K`/`R`（リズムパート）・`{ }`（ポルタメント）・PPZ8**（未解明が実装のブロッカーになる
   度合いが高い3項目。`K`/`R`は14bitマスクの`@`対応、`{ }`は引数バイト構成、PPZ8は
   MML文字→チャンネル番号対応、といずれも「動くが正しさを検証できない」リスクを抱えるため
   最後に回す）。
9. **オクターブ範囲外の再検証**（3.10節の通り、3.1〜3.7が完了して初めて「独立した課題か
   どうか」を判定できるため、実装順としては上記すべての後に位置する）。

## 6.5. 「音色未使用時」の表現とRHYTHM固定領域(2026-08-18、参照`.M`実測で確定)

`tools/pmd-reference/`の参照`.M`(MC.EXE ver 4.8s実測)を直接バイト単位で読み、
自作コンパイラの残り2つの構造差を解消した。

### (1) 音色テーブル終端マーカ

MML本文に`@`定義が1つも無い場合、参照`.M`はトーンテーブル位置(`tone_ptr`)に
**26byteの音色エントリを一切書かず、`00 FF`という2byteの終端マーカだけ**を置く
(`pmdbasic.M`/`pmdhdrmt.M`/`pmdhdrpc.M`の3ケースで確認)。さらにこの`00 FF`は
**音色定義が1件以上ある場合も、最後のエントリの直後に必ず付く終端**であることを
`pmdtone.M`(`@1`1件)・`pmdton2.M`(`@2`1件)で確認した。つまりトーンテーブルは
「エントリ0個以上 + `00 FF`終端」という一貫した形式で、`@`未使用は単に0エントリの
特殊ケースに過ぎない。自作コンパイラ(`compiler/pmd_mml_compiler.mjs`)は元々この
終端マーカを一切出力しておらず(エントリの有無に関わらず)、`@`未使用時は後方互換の
ため既定音色`@1`(26byte)を常に合成して埋めていた。今回、出力側では
`hasExplicitTones`(利用者が実際に`@n`定義か`tones`オプションを与えたか)で
分岐し、無ければ`00 FF`終端マーカのみを置くよう修正した。検査(validation)側の
既定音色合成(`toneTable[1]={}`)は後方互換のため維持している
(`tools/verify_pmd_recompile_after_error.mjs`のFIXED_MML='A o4 c4 d4 e4 @1'
のように、`@n`定義ブロック無しで`@1`を選択するMMLが既存検証に存在するため。
出力にだけ反映しないことで、この検証を壊さずに済んだ)。

### (2) RHYTHM/r_offset固定領域

ヘッダの`r_offset`(相対オフセット`0x16`、`fmdriver_pmd.c:281,5440`で
`pmd->r_offset + cmd*2`としてK/Rパートのパターン定義ポインタテーブルとして
参照される)が指す先に、参照`.M`は**K/Rパートを一切使わない曲でも常に8byteの
領域を確保する**ことを、`pmdunimp.M`(K/R使用、除外)を除く全18ケースで確認した
(`r_offset`から`tone_ptr`までの距離が全ケースで12byte=この8byte+flags4byte、
という不変式で確認)。うち先頭から7byte目以降(index1-7)は**全ケースで`0x00`固定**。
先頭byte(index0)は`0x16`〜`0x80`の間でケースごとに揺れており、単純なMML内容
(使用パート構成・T値・使用コマンド)との相関を確認したが規則を特定できなかった
(K/R自体が未実装のため実害の無い値と見られ、MC.EXE内部の未使用パターン0番
ポインタの残留値の可能性がある)。指示書が名指しした3ケース(`pmdbasic.M`/
`pmdhdrmt.M`/`pmdhdrpc.M`)はいずれも`0x60`で一致していたため、既定値として
`0x60 00 00 00 00 00 00 00`を採用した(`compiler/pmd_mml_compiler.mjs`の
`rhythmFixedAddr`まわり)。自作コンパイラは元々この領域を1byte(0x80、他の
未使用パートと同じ扱い)しか確保していなかった。

### (3) 配置順序の訂正(当初の想定と異なっていた)

上記2点を実測する過程で、メモテーブル(#Title等、`buildMemoTail()`旧
`buildMemoBlock()`)の実際の配置が、当初の実装が想定していた「`tone_ptr`の
**手前**」ではなく「`tone_ptr`が指すトーンテーブルの**直後**」だったと判明した
(`pmdbasic.M`/`pmdtone.M`/`pmdhdrmt.M`/`pmdhdrpc.M`の4ケースで確認)。
実際のファイル順序は
`[トラック][r_offset固定領域8B][flags4B(toneptr-4)][トーンテーブル][メモ文字列群][メモポインタテーブル]`
であり、flagsが指す`memoTableOff`は末尾のポインタテーブルを指す。この訂正込みで
`compileMml()`のカーソル計算を書き直した。

### 結果と未解明ブロッカー(新規発見)

上記(1)(2)(3)を反映した結果、ヘッダ〜トーンテーブルまでの全バイトが参照`.M`と
完全一致することを確認した(`pmdbasic.M`等でヘッダ26byte+r_offset8byte+flags4byte+
トーンテーブルまで手動バイト突き合わせ済み)。しかし**この作業と同時に、既存の
別課題(今回のスコープ外)がトラック本体(音符バイト)に残っていることが判明した**:
`o`コマンドで指定したオクターブ値がそのまま(octave<<4)|noteIndexへ符号化されて
いるが、参照`.M`は**常にこれより1小さいオクターブ値**で符号化している
(`pmdbasic.mml`の`o5`→自作`0x50`/参照`0x40`など、ヘッダに`#Title`を持つ8ケースで
差分が全て`±0x10`(1オクターブ分)であることを確認、後述)。この差は`compare_pmd_m.mjs`の
パート一致判定(`PART_NAMES`の11パートのみを比較範囲とし、トーンテーブル領域は
比較対象に含まれない実装上の制約)には現れないが、実際のノートバイトは不一致のため
`node tools/verify_pmd_reference_corpus.mjs`の`identical:true`(パート一致11/11)には
現状どのケースも到達しない(最良で10/11、RHYTHM/K以外の実データパートが1オクターブ
ずれて不一致)。このオクターブ差は`git stash`で退避した変更前のコンパイラでも
再現する**既存のバグ**であり、今回の指示書の範囲(①②)には含まれていないため
未修正のまま報告する(`tools/verify_pmd_min.mjs`等の既存検証はpmdweb実機再生で
`noteByte(oct,note)=(oct<<4)|note`の符号化そのものは検証済みだが、MMLの`o`
コマンド値をそのままoctaveとして使うか`o値-1`にすべきかは別問題で未検証)。

## 7. オクターブ符号化の訂正（2026-08-18、公開後に発覚した既存バグの修正）

6章末尾で「未修正のまま」と報告していた、`o`コマンドの符号化バグ（自作は`o`の数値を
そのまま音符バイトのnibbleに使うが、参照`.M`はそれより1小さい値を使う）を今回修正した。
このバグは公開中の実害があった（他所で書かれたPMD MMLを自作コンパイラに通すと
1オクターブ高く鳴る）。

### 確定した符号化規則（参照`.M`実測で確認）

- **`o`コマンドの範囲は1-8（PMDMML.MAN §4-4通り）、既定値は4**。音符バイトのnibbleは
  「`o`の数値 - 1」（0-7）。根拠: `tools/pmd-reference/pmdbasic.mml`（`o5 l8 cdefgab>c<`）
  の参照`.M`で、`o5`区間の音符バイトが`0x40,0x42,0x44,0x45,0x47,0x49,0x4b`（nibble=4）と
  一致した。
- **`<`/`>`は標準MML慣習の向き（`<`=オクターブ下、`>`=オクターブ上）**。旧実装は逆
  （「未検証」コメント付き）だった。根拠: 同じ参照`.M`で、`b`(nibble4=0x4b)の直後の`>c`が
  `0x50`(nibble5)になっている(`>`で1つ上がっている)。
- **既定オクターブ（`o`未指定時）のnibbleは3**（旧実装は4のままだった。`o`コマンドの
  符号化規則と整合させるため、既定値もPMDMML.MAN §4-4の既定`o4`に合わせて1小さくした）。

### 完全一致したケース

## 8. K/R(リズム)実装(2026-08-18、5章の未解明を実測で解消・実装)

確定し、`compiler/pmd_mml_parser.mjs`/`compiler/pmd_mml_compiler.mjs`に実装した。

### 8.1 `\b\s\c\h\t\i`とビット位置、`\l\m\r`とパン値の対応(確定)

新規corpusケース(各音を1音ずつ分離して`\b r4 \s r4 \c r4 \h r4 \t r4 \i r4`のように
出力させる。値を非対称にする既存方針に従い、1音ずつ分離することで対応が一意に決まる)を
MC.EXE ver4.8sで実測し、既存`pmdunimp.M`(複数音の組み合わせ、独立した3パターン)とも
突き合わせて確定した:

- `b`=bit0, `s`=bit1, `c`=bit2, `h`=bit3, `t`=bit4, `i`=bit5(マニュアル記載順そのまま)
- `\v`の対象music番号(1-6、0xeaの上位3bit): `b`=1,`s`=2,`c`=3,`h`=4,`t`=5,`i`=6
- `\l`=0b10(2), `\m`=0b11(3), `\r`=0b01(1)(YM2608パンレジスタのLL/RR2bitと同じ並び)

複数の`\`系ショットコマンドが間に何も挟まず連続すると、参照`.M`は単一の0xebバイトへ
ビットを合算する(`\b\c`→`eb 05`)。マスタボリューム(`\V`)は既に確定済み(1.3節参照)。

### 8.2 `r_offset`固定領域の正体(訂正)

6.5節で「r_offsetの8byte固定領域」としていたものは、実は**r_offsetそのものではなく、
r_offsetの直後(K/R使用時は索引表+パターン本体の直後)、tone_ptrの手前に常にある
別の8byte領域**だった。K/R未使用時はr_offsetの値がこの領域の先頭アドレスと一致する
ため区別できていなかった。`pmdunimp.M`実測で正しい構造を確定:

```
r_offset → [索引表(パターン番号ごとに2byte、番号0から連番)][各パターン本体(`\`系
  コマンド列 + 単独0xff終端)] → (常にある8byte領域、K/R未使用時0x60他0固定・
  K/R使用時は実測上も先頭byteが0x00/0x90等ばらつき、依然未解明) → flags/toneTable
```

この8byte領域自体の意味・先頭byteの規則は依然未解明のまま(K/R使用時も先頭byteが
`pmdunimp.M`で0x00、新規`pmdrhbit.M`/`pmdrhpan.M`で0x90とばらつき、音には影響しない
ことをpmdweb実測で確認済み)。

### 8.3 実装範囲

- Kパート: `R数値`(パターン選択、cmd<0x80制約により0-127のみ受理)・ループ(`[ ] :`)・
  全体ループ(`L`)・`\`系コマンドを実装。他パート文字との同一行混在(実データで多用)に
  対応し、`C`(全音符長)は処理、`o`/`<`/`>`/`l`/`v`/`V`/`q`/`_`/`__`はK自体には出力が
  無いため構文だけ受理して読み捨てる。
- Rパターン本体: 休符(`r`)・デフォルト音長(`l`)・ループ・`\`系コマンドを実装。
  `@音色番号`によるPMD内蔵SSGドラムのマスク指定方式(§6-1-3)は実データに1件も出現せず
  未実装のまま(専用エラーで停止)。
- Rパターン番号は0から連番であることを要求(飛び番号は未実測のため未対応、専用エラー)。
- 副産物: ループ(`0xf8`)のカウンタ初期値が従来0固定だったのを`pmdunimp.M`実測で
  `count`と同値に訂正(コンパイル直後のスナップショット値。ループ使用corpusは
  `pmdunimp`のみで退行なし確認済み)。これにより`pmdunimp.M`がバイト完全一致になった。
