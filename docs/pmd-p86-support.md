# PMD86 `.P86` PCM対応 — 実測記録

2026-08-19 に実装した、PMD86用PCM(`.P86`)の変換対応(JS側で疑似`.PPC`へ
変換して既存経路に流す方式)の測定経緯をまとめた記録。実装そのものの結線は
`docs/pmd-pcm-support.md`(特に§3)を参照。本文書は「なぜこの方式にしたか」
「なぜリサンプル不要と確定できたか」という**測定の裏付け**に絞る。

対応するコミット: `4dfbcf4`(変換器・第1段階)、`ff2d6f2`(結線・第2段階)。

---

## 1. `.P86` の形式(実測)

参照実装のソース(`upstream/pmdmini/src/pmdwin/`)は権利上読んでいない。
`.P86` サンプルデータ本体の実測とヘッダ構造の逆算から特定した(`net/pmd-p86.js`
冒頭コメント・`parseP86()` 実装参照)。

- ヘッダ: マジック `"PCM86 DATA\n\0"`(12B) + version `0x11`(1B) +
  全体長3B(LE) = 計16B
- テーブル: 256エントリ × (開始オフセット3B(LE) + 長さ3B(LE)) = 1536B
  (16B + 1536B = 1552B = `0x610`)
- データ本体: `0x610` から開始
- サンプル形式: **符号付き8bit**

符号付き8bitと判定した根拠(実測):
- 無音区間・末尾のサンプル値が `0x00` に収束する(符号付き8bitの無音値と
  一致。unsigned 8bitの無音値なら `0x80` に収束するはず)
- unsigned として読んだ場合、データ全体の平均値が128付近(符号なし8bitの
  中央値)になってしまい、音声波形として辻褄が合わない(直流成分が
  乗ったまま再生されることになる)

---

## 2. 方式の選択: 本物のP86再生器は実装しない

`.P86` を扱うには2つの道があった。

1. PMD86ドライバのADPCM(YM2608 ADPCM-B)への直接書き込みロジックを
   独自実装し、`.P86` をネイティブに再生する
2. JS側で `.P86` → 疑似 `.PPC`(YM2608 ADPCM、upstreamが元々対応している
   形式)へ変換し、既存の `pmd_ppc_load()` にそのまま流す

2を選んだ。理由:
- upstream(`upstream/98fmplayer/`)の C コードを一切変更せずに済む
  (`fmdriver_pmd.c` の `pmd_ppc_load()` 経路は既に動いている)
- GPL の PMDWin 系実装(`upstream/pmdmini/src/pmdwin/`、特に `p86drv.cpp`)
  に触れる必要がない。読まずに済む設計を最初から選べた

`.PPC` はYM2608 ADPCM-B形式で4bit差分符号化が要るため、`.P86` の8bit
サンプルをADPCM-Bへエンコードする変換器(`net/pmd-p86.js` の
`encodeAdpcmB()`)を実装した。エンコードアルゴリズムは upstream
`libopna/opnaadpcm.c` の復号処理をそのまま読み取り、その逆写像として
実装している(推測でパラメータを決めた箇所はない)。

## 3. リサンプル不要(1:1)と確定した経緯

ここが今回の測定の要点。

### 3.1 最初の物差しは誤りだった

最初は「MMLの音名から計算した期待周波数」と、変換後に鳴った音の実測
周波数を比べる**自己参照の物差し**で測り、補正係数 0.8763 を得た。

しかしこれは誤りだった。PCMバンクの各サンプルは録音時点で固有の音高を
持っており(サンプルそのものが特定の音の波形)、MML側はそれを前提に
音符を割り当てて書かれている。したがって「音名から計算した期待周波数」
と比べても、**「変換のレート規約がずれている」のか「そのサンプルが
元々その音高で録音されている」のかを区別できない**。この物差しでは
補正係数の意味そのものが不定であり、0.8763 は採用しなかった。

### 3.2 別プロセスのオラクルによる測定

参照実装 pmdmini(`.P86` をネイティブ再生できる実装)を**別プロセスの
オラクル**として使い、以下を比較した(`tools/experiment_pmdmini_oracle_check.mjs`
/ `tools/experiment_pmdmini_oracle_compiled.mjs`):

- (A) pmdmini + 本物の `MBE86PCM.P86`(ネイティブ`.P86`サポート)
- (B) 我々のwasm経路 + 疑似`.PPC`(1:1変換、`tools/experiment_p86_to_ppc.mjs`)

両者に**全く同じ `.M` ファイル**(ADPCM単独パート、同じtonenum/音符)を
食わせ、出力波形の基本周波数比(A:B)を取った。サンプル固有ピッチ(f0)は
A/Bで完全に同一の入力データを参照するため比較の両辺から相殺され、残るのは
「レート規約の違い」だけになる、という設計。

結果、高信頼5件の周波数比(実測/期待)は
**1.032 / 1.051 / 1.070 / 0.928 / 1.110**(平均1.038、変動係数5.9%)。
1.00を挟んでばらついており、**系統的なずれは検出されなかった**。

ピッチ検出器自体は正弦波(110〜1046Hz)で誤差0.049%、オクターブ比も
0.049%以内と別途検証済みのため、検出器側の誤差が主因ではない。上記の
ばらつきは実楽器サンプルの非周期性(倍音構成・アタック/ディケイの影響で
自己相関ベースの基本周波数推定が振れる)に由来すると判断し、
**サンプルレート変換(リサンプル)は行わず、`.P86`の8bitサンプル列を
そのまま1:1でADPCM-Bへエンコードする**方式を確定した。

### 3.3 権利上の線引き(厳守)

- upstream/pmdmini は**ビルドして実行ファイルを`child_process`で呼び、
  出力される波形(WAV)を測定に使うだけ**
- `upstream/pmdmini/src/pmdwin/` のソース(特に `p86drv.cpp`)は一切
  読んでいない。ビルド方法・コマンドライン引数の意味・WAV出力形式
  (44100Hz/16bit/stereo、ヘッダ44byte)は `CMakeLists.txt` /
  `README.md` / `sdlplay.cpp` / `src/pmdmini.h`/`.cpp`(いずれも
  pmdwin外)から得た
- 自分たちのコードに pmdmini をリンクしていない。ビルド成果物は
  `upstream/pmdmini/build/` に置き、`dist/` には混ぜない(このディレクトリは
  `upstream/` ごと `.gitignore` 対象で追跡もしていない)

## 4. 踏んだ落とし穴: ADPCM RAMのアドレス単位

`.PPC` 形式のオフセットテーブル(start/stop)を書き出す際、当初
「1レジスタ = 4バイト」と誤読して測定を1回丸ごと無駄にした。

実際には**1レジスタ = 32バイト**が正しい。PMDドライバはADPCM初期化時・
ノートオン時に**常に**control2レジスタへ `C2_8BIT` ビット(`0x02`)を
立てるため、`libopna/opnaadpcm.c` の `addr_conv()` は8bitモード相当の
変換(`reg << 6` をバイト換算すると `(reg << 6) >> 1 = reg * 32`)になる。

発覚の経緯: レジスタを直接叩く最小再現コードで、**内容(サンプルデータ)
に依存しない一定の波形**が出るという不自然な結果になり、そこから
アドレス変換式の誤りに気づいた。値が「それらしく」見えるのに波形が
入力を反映しない、という食い違いが手がかりになった。

## 5. 容量制約

- YM2608 ADPCM RAMは256KB固定
- 先頭 `0x4c0`(1216B)は `pmd_ppc_load()` が実データ書き込み前に
  無条件でゼロ埋めする予約領域(レジスタ換算で `1216/32=38` レジスタ目
  まで)
- 成立すべき不等式(変換後データがADPCM RAMに収まること等)は
  `net/pmd-p86.js` にコードとして実行時検査を書き出してあり、
  故障注入テスト(意図的に容量を超えさせて検査が確実に落ちることの確認)
  済み

実データ `MBE86PCM.P86`(233,662B、8bit)はADPCM-B化(4bit)により
約半分のサイズになり、上記の制約内に収まることを確認している。

---

## 6. E2Eの数字

`kckor_reb.M` + `MBE86PCM.P86` の組み合わせで、変換後の`.PPC`経由再生の
absSumは **685,249,590**。

陰性対照(同じ曲を `.P86` なしで再生。PCM不足のまま無音相当になる場合の
absSum)は **996,576**で、両者は3桁以上のオーダーで乖離しており
「鳴っているように見えて実は鳴っていない」無言の失敗ではないことを
確認している。

---

## 7. 未対応のまま残るもの

- **`.PPS`(PPSDRV用PCM)**: upstreamのC側がこのスロットの読み込み自体を
  実装していないため、変換の入口以前の問題として未対応
- **`.pwi`/`.owi`**: FMPドライバ(fmplayer)側が使うPCMデータ形式。
  FMP側は現状 PVI/PPZ のみ対応で、これらは未対応
