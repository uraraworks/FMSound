# PMD MML コンパイラ 回帰用参照corpus

自作 PMD MML コンパイラ(`compiler/pmd_mml_compiler.mjs`)の回帰検証用データ一式。
`node tools/verify_pmd_reference_corpus.mjs` から使われる。

## 中身

- `*.mml` — **すべて自前で書いたMML**(第三者データ・実在曲の流用は無し)。1機能1ファイルの小さな断片。
- `*.M` — 対応する参照出力。PMD公式コンパイラ `MC.EXE` ver 4.8s で実際にコンパイルしたバイト列。
- `baseline.json` — 「現時点の自作コンパイラの一致状態」のスナップショット。回帰検出の基準。

**`MC.EXE` 本体・PMD配布物一式はここには含めていない(同梱・コミット禁止)。**
入手元: PMD公式サイト http://www5.airnet.ne.jp/kajapon/tool.html
(配布zip内の `MC.EXE`。バージョンは実行時のバナー表示で確認: `ver 4.8s`)

**注意: `PMDMML.MAN`(マニュアル)本体も同じ理由でリポジトリに含めていない**
(`docs/pmd-compiler-spec.md` 0章の既存方針: KAJA氏の許諾表現が正式なOSSライセンス
文言ではないため安全側に倒している)。この corpus の `*.mml` は、コマンドの書式を
マニュアルで確認した上で**内容(音・数値・パターン)はすべて自前で作った**もので、
マニュアルの「[例]」ブロックをそのまま書き写したものは無い(2026-08-18、レビューで
`pmdunimp.mml`・`pmdporta.mml` 等が例文の値そのままになっていたのを見つけて
差し替え済み)。

## 設計方針: 値をすべて非対称にする(最重要)

2026-08-18、自作コンパイラが音色定義の **op2とop3を入れ替えて出力する不具合**を、
v1公開後まで検出できずにいたことが判明した。原因は、それまでのテストに使っていた
音色データが4オペレータとも同じ値(対称)で構成されており、内部で順序を入れ替えても
出力バイト列が変わらなかったこと。**「対称なデータは陰性対照にはなっても検出力が
ゼロ」**という教訓のもと、この corpus は最初から同じ穴を踏まないよう設計している。

- 音色定義(`@n`)は4オペレータすべて、AR/DR/SR/RR/SL/TL/KS/ML/DT/AMSを**互いに違う値**にする。
  (`pmdtone.mml`・`pmdton2.mml` を参照。特に「op2とop3を入れ替えると必ず結果が変わる」
  ことが目的なので、op2とop3の値を意図的に大きく離してある)
- パラメータが複数並ぶコマンド(`D`/`DD`・`p`・`q`・`M`・`(`/`)`・`_`/`__` 等)は、
  各要素を違う値にする(同じ値の繰り返しにしない)。
- 複数パートを使うファイル(`pmdmulti.mml`)は、パートごとに音量・オクターブ・音長・
  音符を全部変えている。

新しいcorpusケースを追加する場合も、この方針(非対称データ)を必ず踏襲すること。

## `/V` オプションの扱い

参照`.M`はすべて **`MC /V <name>` (音色データ添付オプション付き)** で生成した。
根拠: 配布物同梱の `SAMPLE.MML` を条件を変えて2通りコンパイルし比較した結果、

- `/V` **無し**: 配布物同梱の `SAMPLE.M`(1142 bytes)と**バイト不一致**(1138 bytes、
  先頭からいきなり差分)
- `/V` **あり**: 配布物同梱の `SAMPLE.M` と**バイト完全一致**(`cmp` で確認済み)

自作コンパイラは常に音色データを添付する流儀(同梱サンプルで音色テーブル先頭ポインタが
`0x001b` 相当になる構成)のため、参照側も構造を揃えるべきという判断で `/V` を採用した。

## 既知の差分(現状メモ、実装作業の参考用)

現時点(baseline.json 生成時点)では、この corpus の大半のケースで自作コンパイラの
出力と参照`.M`は **パート単位で完全一致していない**(`baseline.json` の
`matchedParts` はほぼ 0/11)。実データ(既存の `tools/verify_pmd_compiler_oracle.mjs`
の `PMD_REF_PAIRS` 経由の検証等)ではもっと高い一致率が出るケースもあるため、これは
「corpusが壊れている」のではなく、**現在のギャップをそのまま記録している**状態。
主な要因(`/V`付きの実出力を実際に確認して分かったこと):

- 参照`.M`は未使用パート(FM2-6・SSG1-3・ADPCM)を**それぞれ独立した1byte(`0x80`)の
  プレースホルダ**として個別に配置する。自作コンパイラは複数の未使用パートで
  **同じ空トラックアドレスを共有**する(スペース節約の簡略化)。この違いにより
  `tools/compare_pmd_m.mjs` のパート範囲推定(共有プレースホルダ検出)が早期に
  効かなくなり、比較が浅い場所で早々にズレる。
- 参照`.M`はRHYTHMパートに常に**13byte程度の固定領域**(デフォルトのリズム音源
  パラメータ用と思われる)を持つ。自作コンパイラは未使用RHYTHMを1byteの空トラックとしか
  扱っていない。

これらは**このcorpus作成作業のスコープ外**(コンパイラ実装の変更はしていない)。
将来コンパイラ側でこのギャップを埋めた際は、`--update-baseline` でスナップショットを
更新すること。

### 2026-08-19 追記: r_offset固定領域(8byte、K/R未使用時)の先頭byteの正体を特定・修正

上記「13byte程度の固定領域」のうち、K/R未使用時に常に存在する8byte領域(r_offsetが
直接指す位置)の先頭byteは、**「全パート(FM1-6/SSG1-3/ADPCM、および`#PPZExtend`で
宣言されたPPZ8パート)のうち、最も総クロック数(曲の長さ)が長いパートの総クロック数の
下位8bit」**だと判明した(残り7byteは常に`0x00`で意味は依然未解明)。

根拠: 新規9ケース(`pmddt`/`pmdsl`/`pmdsl2`/`pmdefm`/`pmdnoise`/`pmdwecho`/
`pmdwecho2`/`pmdwecho3`/`pmdmpover`)は、ファイル長・他バイトが完全一致するのに
このbyteだけ自作の固定値`0x60`(96)と参照(`0x18`=24または`0x30`=48)が食い違って
いた。各ケースの「最も長いパートの総クロック数」を数えると参照値と完全に一致し
(既存corpus`pmdtone`等が偶然96クロックにそろっていたため無症状だっただけと判明)、
corpus全43ケースで突き合わせても、K/R使用の3ケース(`pmdrhbit`/`pmdrhpan`/
`pmdunimp`、r_offsetが索引表という別構造になるため対象外)を除く全40ケースで
この定義が成立した(`pmdwhole.mml`はl4等のデフォルト音長が`C`(全音符長)変更に
追従しない既存の別バグにより元々100%不一致のため対照外)。

ループ(`[`...`]n`、`:`で脱出区間を分ける)を含む`pmdloopx.mml`(4パート、単純
ループ・2重ネスト両方を含む)でも実測し、総クロック数の数え方を確定した:
`:`が無ければ本体を n 回展開してそのまま加算。`:`があれば「最終回(n回目)だけ
`:`〜`]`の区間を再生せず抜ける」(0xf7 `:` の実行時挙動どおり)ため、
`before×n + after×(n-1)`(before=`:`より前、after=`:`〜`]`の区間)になる。
ネストしたループは、内側の展開後クロック数を外側の1イベント分として加算する。
この式で`pmdloopx`の4パート全てが参照.Mの値と一致することを確認済み。

実装は`compiler/pmd_mml_compiler.mjs`の`computeLongestPartTicks()`/
`trackTotalTicks()`(固定値`0x60`のハードコードを廃止)。この修正により、上記
9ケースを含む多数のcorpusケースが完全一致に改善した(`--update-baseline`実行済み、
`baseline.json`参照)。

## 未実装機能(意図的に「今は一致しない」を記録している)

- `pmdunimp.mml`: `K`/`R`(SSGリズムパート)。書式(`\b`/`\s`/`\h`/`\t`/`\c`等の
  リズム音源ショット・個別音量、`K`パートでの`R`コマンドによる演奏順指定、
  `R0`/`R1`/`R2`というパターン定義パート)は PMDMML.MAN §1-2・§6-7・§14 で
  確認したが、**パターンの中身・演奏順・音量値はすべて自作**(3パターンとも
  使用するリズム音・音長・繰り返し回数を互いに違えてあり、パターン番号を
  取り違えると検出できる)。実機コンパイラは問題なく通るが、自作コンパイラは
  `K`/`R` パート指定自体を未対応としてエラーを返す
  (`compiler/pmd_mml_parser.mjs` のコメント参照)。
- PPZ8拡張パート(`#PPZExtend`)は2026-08-18に実装・corpus追加済み(`pmdppzord.mml`
  「#PPZExtend cba」・`pmdppzsub.mml`「#PPZExtend edc」・`pmdppznote.mml`、いずれも
  MC.EXE ver4.8s `/V`実測)。パート記号とPPZ_1〜_8の対応は「#PPZExtendでの宣言順」
  (記号自体の固定値ではない)と確定した。`pmdppzord`/`pmdppzsub`は11/11パート一致・
  バイト完全一致(2026-08-19、r_offset固定領域先頭byteの正体判明・修正により
  `pmdppzsub`も完全一致に到達。上記追記節参照)。`pmdppznote`はr_offset固定領域自体は
  一致するが、PPZ8関連の別要因(未解明)で全体一致には至っていない。詳細はdocs/pmd-compiler-spec-v2.md
  2章を参照。
- FM3拡張パート(`#FM3Extend`)は2026-08-19に実装・corpus追加済み(`pmdfm3a.mml`
  「宣言なし」・`pmdfm3b.mml`「#FM3Extend xy、2パート」・`pmdfm3c.mml`
  「#FM3Extend xyz、3パート」・`pmdfm3d.mml`「宣言のみ・未使用」・`pmdfm3e.mml`
  「パートA自体にも音符あり」、いずれもWebNP2上のMC.EXE ver4.8s実測(`/V`)。
  `0xc6`(FM3拡張初期化、3スロット×2byteポインタ)は**パートA(FM1)のトラック先頭に
  前置**され、パートAに中身があればその直後にA自身のイベントが続く。拡張パート自身の
  トラック本体は`#PPZExtend`のPPZ8パートと同じ位置(RHYTHMスロット直後・r_offsetの
  手前)に置かれ、宣言だけで未使用の文字も他の未使用パートと同様に空トラック(`0x80`)
  として実体を持つ。5ケースすべて11/11パート一致・バイト完全一致。
  `#PPZExtend`と`#FM3Extend`を同時宣言する組み合わせ(実データ`MSO_FM_FS_PPZ.MML`で
  実在)は、参照`.M`の構造読み取りで「FM3Extendパート群→PPZ8パート群」の順に並ぶことを
  確認し、その順で実装した(この組み合わせ自体を再現するMC.EXE実測corpusは無く、
  実データの参照.M構造からの読み取りのみが根拠。詳細は
  `compiler/pmd_mml_compiler.mjs`のidx===10ブロックのコメント参照)。

## ヘッダ命令(`#Title`/`#Composer`/`#Memo`/`#PCMfile`/`#PPZfile`)のメモテーブル形式

2026-08-18、`pmdhdrmt.mml`(`#Title`/`#Composer`/`#Memo`のみ、PCM系ヘッダ無し)の
参照`.M`を実測し、`compiler/pmd_mml_compiler.mjs`の`buildMemoBlock()`の前提だった
「PCM系ヘッダが無ければ旧レイアウト(flaglow=0x40・4スロット)」という条件分岐が誤りだと
判明した。実際のMC.EXEは**PCM系ヘッダの有無に関わらず常に**
`[PPZ, PPS, PCM(予約), Title, Composer, Arranger, Memo...]`という8スロット構成 +
`flaglow=0x48`/`flaghigh=0xfe`で出力する(手計算で全8スロットの文字列オフセットを
`pmdhdrmt.M`と突き合わせて確認済み。詳細は当時の作業ログ参照)。
`buildMemoBlock()`は現在この常時8スロット構成に修正済み。これにより出力ファイルが
若干大きくなり、**PCM系ヘッダを使わない既存corpusケースでも`verify_pmd_reference_corpus.mjs`
のバイト一致率がわずかに低下する**(トラック配置自体は変わらないが、ヘッダ直後の
アドレス値が全体的にずれるため)。これは劣化ではなく「実機によりビット単位で近づいた」
結果であり、`baseline.json`は意図的に更新していない(2026-08-18時点、
`--update-baseline`未実行のまま。実行するかどうかは今後の判断に委ねる)。
`pmdhdrpc.mml`(`#PCMfile`/`#PPZfile`)・`pmdhdrxt.mml`(`#Detune Extend`、
意味未解明のため意図的にコンパイルエラーになる)も同時に追加した。

### 2026-08-18 追記: なぜ `pmdhdrmt`/`pmdhdrpc` はまだ完全一致(バイト単位)しないか

自作出力は参照より17byte長い(`pmdhdrmt`: 243B対226B、`pmdhdrpc`: 158B対141B)。
`tools/compare_pmd_m.mjs`と手計算(参照.Mを`pmd_get_memo()`の実装どおりに
`toneptr-4`→memoptr→テーブル→各文字列と実際にたどって)で内訳を特定した:

- **メモブロック自体(flags 4B + テーブル18B + 文字列139B = 161B)は自作・参照で
  バイト長が完全一致**しており、8スロット全ての文字列も相対位置ベースで内容が
  一致することを確認済み(このファイルの実装ではない)。
- 差分17Bの内訳は2つの**既存・別スコープの問題**の合算:
  1. **RHYTHM固定領域(約7B)**: 参照は常にRHYTHM用の固定領域を持つ(上の「既知の差分」
     節に既述)が自作はRHYTHMを1byteのプレースホルダのみで済ませている。
  2. **`@`未使用時のトーンテーブル表現(約24B差)**: `pmdbasic.M`/`pmdhdrmt.M`/
     `pmdhdrpc.M`いずれも、MML本文に`@`が一切無い場合、参照はtone_ptr位置に
     **2byteの固定マーカ(`00 FF`)** だけを置き、実トーンテーブルを持たない
     (`pmdtone.M`等`@`定義があるケースはtone_ptr位置に実データが来ることを確認済みで
     対照になっている)。自作コンパイラは`@`が無い場合でも後方互換のため
     既定音色`@1`(26byteの実エントリ)を常に1つ合成しており、この差が24byte。
  3. 24B(2.) − 7B(1.) = 17B(観測された差分と一致)。
- どちらも**ヘッダ/メモ実装のバグではない**。(1)はRHYTHM(`K`/`R`)未実装という
  既知の対応不能事項、(2)は「`@`未使用時のトーンテーブル省略」という、ヘッダ機能とは
  無関係な既存の別課題(直すには全corpusケース・多数の検証スクリプトへの影響調査が要る)。
  そのため今回はどちらも直していない。`identical: true`には届かないが、
  **`tone_ptr`(offset25)以降の食い違いはメモ内容の誤りではなく、この2つの
  上流バイト数差がアドレス値をずらしているだけ**、というのがここまでの結論。

## 再生成手順

前提: WebNP2(PC-98エミュレータ、`WebNP2/`)を dev サーバーで起動し、MCPブリッジ経由で
ブラウザ操作できる状態にすること。手順・スクリプト一式・ハマりどころは
`tools/webnp2-mc-pipeline/`(`MEMO.md`/`README.md`)に保全してある。要点のみ記載する。

1. `WebNP2/` を `npm run dev` 等でローカル起動する(`http://localhost:5173/?bridge=1`)。
   公開ページ(`https://uraraworks.github.io/WebNP2/?bridge=1`)からは
   Private Network Access制限で `ws://127.0.0.1:*` のMCPブリッジに繋がらない実績がある。
2. WebNP2のMCPサーバー(`server.mjs`)をstdioで起動し、HTTPブリッジ経由(`POST /call`)で
   叩けるようにする(MCP未登録でも動く。`claude mcp add` 等の設定変更は不要)。
3. WebNP2の「FreeDOS(98)で起動」を押し、`A:\>` プロンプトが出るまで待つ
   (`booted`イベント後でないとMCPブリッジは繋がらない)。
4. FD2に空FD(FAT12)を挿入 → `MC.EXE`(手元で用意した公式配布物、リポジトリ外)を書き込み。
5. 各 `*.mml` を **CRLF改行で**(重要。LFのみだと `MC.EXE` が全体を1行として誤認し
   `MML中に理解不能な文字があります`エラーになる)8.3形式のファイル名でFD2に書き込み、
   `B:\>MC /V <stem>` を実行して `Compile Completed.` を確認、`<stem>.M` を読み出す。
6. 取得した `.M` をこのディレクトリに `<stem>.M` として保存する。
7. `node tools/verify_pmd_reference_corpus.mjs --update-baseline` で `baseline.json` を
   更新する(自作コンパイラ側の出力が変わった場合のみ。参照`.M`を差し替えただけなら
   diffを確認してから更新すること)。

## 2026-08-18 追記: `pmdmp.mml`(MP/MPA/MPB)・`pmdq1b.mml`(qの数値1)

実データ3曲(第三者MML、リポジトリ非同梱)の残エラーのうち「M書式バリエーション」の実体が
`MP`/`MPA`/`MPB`(`PMDMML.MAN §9-6`、上昇/下降専用LFO指定)だったと判明し、`pmdmp.mml`で
専用corpusを追加した(数値1のみ非対称2値、LFO1/LFO2の両方をカバー)。同様に`q`の数値1
(固定カット量)も`pmdq1b.mml`で解明・実装し(`0xfe`にそのまま1byte)、数値1+数値2の組合せで
数値2側(`0xb1`)の既存実装の計算式の誤り(「数値2そのもの」ではなく「`|数値1-数値2|`」が
正しい)も副次的に見つけて修正した。詳細は`docs/pmd-compiler-spec-v2.md` 3.3/3.6/5章参照。
`pmdmp.mml`は当時、RHYTHM領域のr_offset固定領域先頭byte(参照.M実測でこのケースだけ
`60`ではなく`30`になる、原因未特定)により100%完全一致には届いていなかった
(FM1/FM2=MP関連バイトは完全一致)。この原因は2026-08-19に判明・修正済み(上の
「r_offset固定領域(8byte、K/R未使用時)の先頭byteの正体を特定・修正」節参照。
「最も長いパートの総クロック数」の下位8bitで、`pmdmp.mml`は最長パートが48クロック
=`0x30`だった)。`--update-baseline`後は`pmdmp.mml`も100%完全一致。`pmdq1b.mml`は
元から100%完全一致。

## 2026-08-19追記: SSG `P`(pmdptbl.mml)・Rパターン休符長(pmdrrdef/pmdrr96/pmdrr192/pmdrrl8/pmdrrl8b.mml)

- `pmdptbl.mml`(`PPTBL.MML`実測): SSG(G/H/I) `P`(トーン/ノイズ選択)の`0xed`引数byteが
  `P1→0x07`/`P2→0x38`/`P3→0x3f`(0x07|0x38)という非線形変換であることを確定した
  (旧仮実装はMMLの数値をそのまま出力しており誤り)。
- `pmdrrdef.mml`(l指定無し・既定C96)/`pmdrr96.mml`(K行に`C96`明示)/`pmdrr192.mml`
  (K行に`C192`)/`pmdrrl8.mml`(K行に`l8`)/`pmdrrl8b.mml`(R定義行自体に`l8`)は、
  RHYTHMパターン(`R<n>`)内の無指定`r`(休符)の長さが、その時点のデフォルト音長`l`に
  従うことを確認するための最小構成5本(いずれも`R0 \h r \b r`+`K ... R0`)。
  重要な点は「Rパターン本体はKパートから最初に参照された時点で遅延コンパイルされ、
  参照元Kストリームのその時点のデフォルト音長を継承する」こと(`pmdrrl8.mml`は
  l8がK行側にありRパターン定義行より後に書かれているにもかかわらず休符が12クロック
  になる、という実測結果がこれを裏付けている)。詳細は
  `docs/pmd-compiler-real-data-diff-2026-08-19.md`の「5周目セッション」節を参照。

## 実行

```sh
node tools/verify_pmd_reference_corpus.mjs
```

ベースラインより悪化したケースがあれば非0で終了する。改善(自作コンパイラの一致率が
上がった)は落とさない(`--update-baseline` での更新を促す案内のみ表示)。

## 注意: `.mml` を編集したら参照`.M`も作り直すこと

参照`.M`は`MC.EXE`実測物であり、対応する`.mml`を後から編集する(曲名などタイトル行の
ような無害に見える変更でも)とペアが壊れ、「コンパイラのバグ」に見える不一致になる
(`pmdff1.mml`の`#Title`が実測後に書き換わり、差分の15文字がそのまま15byteのズレとして
現れていた事故が実例。2026-08-19に発覚・修正)。`.mml`を編集したら必ず「再生成手順」に
従って参照`.M`も生成し直すこと。`tools/verify_pmd_reference_title_sync.mjs`で
`#Title`と参照`.M`埋め込み曲名の対応を全corpus横断でチェックできる。
